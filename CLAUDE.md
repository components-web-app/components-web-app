# CLAUDE.md — components-web-app

This is the demo/template application for `@cwa/nuxt`. It runs against the shared Docker API at `https://localhost/_api`.

History lives in the commits and in `CHANGELOG.md`. This file keeps the rules, the current setup, and the traps that aren't obvious from the code.

## Scope

This CLAUDE.md is the primary place to track demo fixes, fixture updates, and template changes needed as a result of module-side decisions. Do not modify application code directly unless explicitly asked.

## Rules and policies

- **Don't restate or override module or bundle defaults in the template** (Daniel, 2026-09-21). If a default is wrong, raise it module- or bundle-side. Example: the template sets no `pageCache` config and no `clearCachesOnSessionEnd`.
- **Docs sync.** Any change to this template must be reflected in the docs project at `/Users/danielwest/Documents/GitHub/_CWA/docs`. After completing work here, always check whether the docs need updating and flag it if so.
- **Remotes:** `origin` = GitLab (deploys the app, mirrors commits and tags to GitHub), `upstream` = GitHub (runs GitHub Actions). **Push to `origin` only.** Pushing to `upstream` can fight the mirror. If the mirror is behind: GitLab → Settings → Repository → Mirroring repositories → sync (↻).
- **Two issue trackers.** Issues are on GitHub (`gh` works against this repo), and GitLab has its own tracker too: `glab issue list -R silverback-web-apps/cwa/components-web-app`.
- **Every change to `main` gets a `CHANGELOG.md` line.** See *Releasing the template*.
- **Measure caching claims against `APP_ENV=prod` config, not just the dev stack.** Dev TTLs are deliberately short and hide problems (see *Page cache*).
- **`README.md` is the public front door (#209): it makes no claim the template doesn't support** (single-server stays "preview" until #211/#212 ship). create-cwa writes its own README for new projects, so the repo's never ships. Its *Versions and support* tables (latest template → bundle/module, and module → minimum bundle) are the public home of the "go together" pairs: update them with every release and every new pair.
- **Comments are one line, two at most** (#131): what the line does or what not to change, with the issue number. The why goes in issues, the CHANGELOG and this file; no measurements, dates or history in comments.

## Releasing the template

**First release: `v2.0.0-alpha.1` (2026-09-24, on `85fd3e5`).** It shares the bundle's major, `2.x`, but keeps its own alpha count. **`create-cwa` shares the template's version**: `create-cwa` X downloads the template, manifest included, from tag `vX`. So every template release is also a `create-cwa` release with the same version. From now on, tag both on the same commit. Dependencies are tagged too: bundle `^2.0@alpha` and `@cwa/nuxt` `^2.0.0-alpha.1`.

**`CHANGELOG.md` is a rule (Daniel, 2026-09-25).** It lives at the repo root, so it's on GitHub:
- **Every change to `main` gets a line under `## Unreleased` before it's pushed.** One short line in the right group (Upgrade notes, Changed, Added, Fixed, Security, Removed), ending with a link to the commit on GitHub, or to the merged PR or MR that brought it. Put anything a downstream project must do by hand under *Upgrade notes*. Use the full SHA in the link.
  - **A commit can't link to itself** (its SHA doesn't exist yet), so add its line in a small follow-up commit, `Changelog: <subject>`, before pushing. Several changes can share one changelog commit. Changelog-only commits get no line of their own.
  - A merged MR or PR gets one line linking to it, not one per commit.
- **A release** renames `## Unreleased` to `## [X.Y.Z-alpha.N](…/releases/tag/vX.Y.Z-alpha.N) - <date>`, and adds a fresh empty `## Unreleased` above it. **That section is the tag's message** (`git tag -a vX --cleanup=verbatim -F <section file>`) **and the GitHub release notes** (`gh release create … --notes-file <section file>`).
- **When a tracked file (the entrypoint, `k8s.sh`, the chart, the Caddyfile) starts depending on new App code, the release's upgrade notes name those files** (`api/src/…`, migrations, `services.php`). Downstream sites copy tracked paths, so without the note the deploy files arrive without the code they run (alpha.43 missed this; the deployment-statuses notifier caught it).
- `create-cwa` projects don't get this file (`alwaysExclude` in `cwa-manifest.json`): it describes the template, not the new project.

To release:
1. Update everything and run the usual checks. Make sure `CHANGELOG.md`'s Unreleased section is complete, then turn it into the version's section. Update the README's *Versions and support* table to the new version and its bundle and module.
2. Set `packages/create-cwa/package.json`'s version to the same `X.Y.Z-alpha.N`, **and `ARG CWA_PHP_BASE=ghcr.io/components-web-app/cwa-php-base:X.Y.Z-alpha.N` in `api/Dockerfile`** (`bin/test/php-base-version.sh` fails otherwise), then commit and push.
3. On that commit, `git tag -a vX.Y.Z-alpha.N --cleanup=verbatim -F <the version's CHANGELOG section>` (without `--cleanup=verbatim` git strips the `### …` headings as comment lines; alpha.14's tag lost them) and `git tag create-cwa/vX.Y.Z-alpha.N`. Push **only the template tag** to `origin` (and only there) for now. A CLI published before its template tag exists fails for every user with "No CWA template found".
   - **3a.** When the tag has mirrored (`gh api repos/components-web-app/components-web-app/git/ref/tags/<tag>`), wait for `publish-php-base.yml` on it to pass (`gh run list --workflow publish-php-base.yml`, `gh run watch <id>`; ~30 min). It publishes `cwa-php-base:X.Y.Z-alpha.N`, which that release's Dockerfile pulls (see *Published php base*). **First publish only:** GHCR packages start private, so github.com/orgs/components-web-app/packages → `cwa-php-base` → Package settings → Change visibility → Public (the org must allow public packages; the REST API can't change visibility).
     **If it fails:** rerun it (`gh run rerun <id> --failed`; a rerun after a failed attestation finds its own tag and attests it). If it needs a code fix (a plugin wanting a newer Go, a failing smoke test), don't push `create-cwa/vX`: fix on `main` and release X+1. vX stays an image-less tag that no CLI installs, and the tag's own Dockerfile can't be republished (plan requires its default to name its own version).
   - **3b.** Then push `create-cwa/vX.Y.Z-alpha.N` to `origin`. Its workflow refuses to publish until the image is anonymously pullable.
4. Run `gh run download <publish-php-base run id> -n php-base-build-info` and append `build-info.md` (the pinned digest, the `gh attestation verify` command, base digests, `php -m`, `frankenphp build-info`) to a copy of the CHANGELOG section, then `gh release create <tag> --verify-tag --prerelease --notes-file <that file>`. `--verify-tag` stops `gh` from creating the tag on GitHub itself, which would fight the mirror.

A plain version tag starts no deploy: every GitLab job is limited to branches or `main`, and the only GitHub workflows on tags are `publish-php-base.yml` (`v*`, publishes the image) and `publish-create-cwa.yml` (`create-cwa/v*`). A release does change what new installs get, through the matching `create-cwa`. `pnpm create cwa my-app -- --ref main` (or `--ref <any tag or branch>`) gets another version of the template. Installs from `create-cwa` 0.x still read the manifest's `branch` (`main`), so leave that field in `cwa-manifest.json`.

## Publishing `create-cwa` to npm

The CLI lives in `packages/create-cwa/`. It is published manually via a git tag; there is no automatic publishing.

1. Set the version in `packages/create-cwa/package.json` to the template release it installs (`0.1.1` was the last 0.x). The workflow publishes it as `latest`, because every release is still an alpha.
2. Commit and push to `origin`.
3. Tag `create-cwa/vx.y.z` and push the tag to `origin`, after `cwa-php-base:x.y.z` is published and public (release step 3a).
4. GitLab mirrors the tag to GitHub → `publish-create-cwa.yml` checks the image anonymously, then publishes to npm via OIDC.

**No stored token.** Publishing uses npm's OIDC Trusted Publishing (configured at `npmjs.com/package/create-cwa/access`: org `components-web-app`, repo `components-web-app`, workflow `publish-create-cwa.yml`).

**A new package's first publish must be local**, because OIDC can't be configured for a package that doesn't exist yet: from the package dir, `pnpm install && pnpm run build && pnpm publish --access public --no-git-checks`. **Don't add `--provenance`** locally (it needs a GitHub Actions runner). **Don't forget `--access public`:** a scoped package's first publish is otherwise private and 404s for everyone (hit with `@cwa/nuxt`; fixed with `npm access set status=public`, then about 90s for npm's cached 404 to clear).

**When to bump:** changes to `packages/create-cwa/src/`, changes to `cwa-manifest.json` that affect the CLI, and **every template release** (since `2.0.0-alpha.1` the CLI downloads the template tag matching its own version, so template changes reach new installs only through a release).

**Updating the bundle:** `composer update components-web-app/api-components-bundle` inside the php container (`api/composer.json` doesn't require API Platform directly, so a plain `composer update` may move it a major). Then `bin/console doctrine:migrations:diff`, generate and commit any migration with the lock, `lint:container` in dev and prod, PHPUnit, `composer audit`, and check pages hydrate. **A `composer update` in the running dev container can cause a few minutes of 500s** while `vendor/` is rewritten; it recovers without a restart.

**Migrations run through `app:database:migrate` (#85),** which the entrypoint calls in every php process that starts (API pods, the orphan-scan and image-variant CronJob pods). It holds a Postgres advisory lock (`pg_try_advisory_lock(hashtext('cwa-database-migrate'))`, on its own connection) around `doctrine:migrations:migrate --allow-no-migration --all-or-nothing` and `ANALYZE`, so processes starting together migrate once; the others wait (`--lock-timeout`, 600 s) and find nothing to do. `tests/Functional/MigrateDatabaseCommandTest.php` runs the real migrations from an empty database and the lock wait.

**Migrations are upward-only (Daniel, 2026-10-08).** Delete the generated `down()` from every new migration; Doctrine's inherited `down()` then aborts (`No down() migration implemented`). A schema change is undone by a new forward migration, never by migrating down.

**Updating the module / front-end deps:** on the host use `pnpm up/remove/dedupe --lockfile-only` (a plain host `pnpm up` fails with `ERR_PNPM_UNEXPECTED_STORE`, because host `node_modules` comes from the container's store), then `docker compose restart app`. Then `pnpm run build` (runs `vue-tsc` via `typescript.typeCheck: true`) and a real-browser hydration check (see *Front end*).

**Check after every dependency change:**
```sh
grep -nE '^  vue@3\.5\.[0-9]+:' app/pnpm-lock.yaml   # must print exactly one line
grep -nE '^  typescript@' app/pnpm-lock.yaml         # must be 6.0.3 only
```

### API Platform's genid map in worker mode (#161, resolved)

API Platform's `SkolemIriConverter` (`/.well-known/genid/…` IRIs, produced by the template's forms and navigation links) wasn't tagged `kernel.reset`, so a FrankenPHP worker kept every embedded object it had generated an IRI for ([api-platform/core#8680](https://github.com/api-platform/core/issues/8680)). Fixed upstream by [#8681](https://github.com/api-platform/core/pull/8681) in 5.0.4 / 4.4.5; bundle 2.0.0-alpha.29 dropped its hotfix (api-components-bundle#500) and requires `api-platform/core ^4.4.5 || ^5.0.4`.
- `tests/Unit/SkolemIriConverterResetTest.php` checks the services resetter clears the map. Keep it: a regression upstream would show there first.
- **A compiler pass that adds a `kernel.reset` tag must run before `ResettableServicePass` (-32).** As `Kernel::process()` (-10000) the tag showed in `debug:container`, but the resetter never called it.
- Measured in a worker simulation over 300 requests to a form component: 41 → 125 MB before the fix, and 44.5 → 44.6 MB on bundle alpha.21. Workers also restart every 500 requests (`FRANKENPHP_LOOP_MAX`).

### Accepted npm advisories (#220)

`app/pnpm-workspace.yaml`'s `auditConfig.ignoreGhsas` is the register of advisories the template knows about and leaves unpatched, one comment line each: package and severity, why it's unreachable on a deployed site (not in `.output/server`, build or dev only), and the upstream fix it waits on. `pnpm audit` then reports them as ignored, and downstream sites inherit the register with the release. **Review it every release** (next look: 2026-11-21): drop an entry once a fix ships, and list what's still accepted in the release's *Security* section. A new advisory goes in only after checking it isn't shipped (`ls .output/server/node_modules/<pkg>` in a production build); one that ships gets an override or a fix, never an ignore.
- **cwa-deployment-statuses watches the register** (hourly, on `main`): when a lock refresh drops an entry's advisory or OSV lists a fixed version, it opens a confidential issue there ("Accepted advisory now fixable: <pkg> <version> (<id>)"), which emails Daniel. Then take the fix, drop the entry from `ignoreGhsas` and the CHANGELOG list, and release; the issue closes itself once `main`'s register no longer lists it.
- **Composer's equivalent is `config.audit.ignore` in `api/composer.json`**, which the same scan reads. Accept a PHP advisory only in the reason form (`{"<id>": "<why it's unreachable; the fix it waits on>"}`), so the reason shows wherever it's read. None today.

### ⚠ TypeScript is pinned to exact `6.0.3`

- Do **not** bump to 7.x. TS 7 is the native (Go) rewrite; `vue-tsc` (3.3.13) still resolves `typescript/lib/tsc` and fails with `ERR_PACKAGE_PATH_NOT_EXPORTED: ./lib/tsc`. **Re-check on every dependency update** (Daniel, 2026-10-13) by watching [vuejs/language-tools#6170](https://github.com/vuejs/language-tools/pull/6170) (content mapper, vue-tsc v4 alpha; a draft on 2026-10-18), the support upstream points to; every TS 7 issue there is closed (#6156, #6124, #5381) with `typescript-native-bridge` as the stopgap. 3.3.13 only adds support for aliasing `typescript` to `@typescript/typescript6`.
- **`pnpm up --latest` DOES rewrite the exact pin to 7.x.** An exact pin is not protection. After it, manually revert to `6.0.3` and reinstall. Prefer `pnpm dedupe`, which doesn't touch it.

### ⚠ Duplicate `vue` copies

A split (two `vue@3.5.x` versions, or one version twice with different `typescript` peers, because vue takes typescript as an optional peer) causes:
- a huge structural `Ref<HTMLElement>`-not-assignable `vue-tsc` error (seen on `useHtmlContent(...)` in `HtmlContent.vue`/`AltHtmlContent.vue`). It can pass locally yet fail CI's `--frozen-lockfile --offline` install.
- **a broken production image at runtime**: `ERR_MODULE_NOT_FOUND … /srv/app/server/node_modules/vue/server-renderer/index.mjs`. All copies collapse onto one Nitro output path and the tracer copies files from the wrong one.
- `nuxt dev` failing with `No fs option provided to compileScript in non-Node environment` (duplicate `@vue/compiler-sfc`).

Diagnose from the lockfile, never `node_modules`. **Fix with `pnpm dedupe`**; aligning typescript to one version is often enough. A `pnpm.overrides` pin on `vue` is the fallback.

Known harmless duplicates: `nuxt` pulls its own `@nuxt/devtools` 3.x beside the 4.0 beta (the beta is loaded), `@nuxt/kit@3.21.8`, and `@nuxt/ui`'s own `@tiptap/*@3.26.1`. Dev logs `NDT_DEP_0003 extendServerRpc is deprecated` from the devtools beta; harmless.

### ⚠ Postgres with no statistics → 30s page loads

- **Symptom:** every page ~30s (erratic: 2s / 4s / 60s), DB CPU high, yet idle-looking I/O. Idle DB CPU, tiny tables and a 99.99% cache-hit ratio are all **consistent with it**; don't "rule out the database" on those signals.
- **Cause:** autoanalyze needs `50 + 0.1×rows` changes, so small component tables stay at `reltuples = -1` forever. Doctrine's `JOINED` inheritance emits a ~30-table hydration query, estimates compound into billions of rows, and the planner (GEQO, randomised) throws parallel workers at it.
- **Diagnose:** `EXPLAIN (ANALYZE, BUFFERS)` and `SELECT relname, reltuples FROM pg_class` (look for `-1`).
- **Fix in place:** the entrypoint's `app:database:migrate` runs `ANALYZE` after the migrations (non-fatal), under the same lock (#85), and `compose.yaml` starts postgres with `-c autovacuum_analyze_threshold=0` (a server flag, because the `app` user can't `ALTER SYSTEM`). Manual: `docker compose exec database psql -U app -d app -c 'ANALYZE;'`. If plan variance ever resurfaces: `-c geqo=off -c join_collapse_limit=30 -c from_collapse_limit=30`.
- The removed `deploy.resources` CPU cap in `compose.yaml` was dead config here (the override's `limits.cpus: '1.5'` wins the merge). It had nothing to do with the slow pages.

### ⚠ Caddyfile edits: truncation, and `adapt` isn't enough

**`frankenphp adapt` only parses; `frankenphp validate --adapter caddyfile` provisions every module, so it catches what `adapt` passes:** a `#` inside CEL (`compiling CEL program`) and Mercure refusing a second unnamed hub (#113) were both clean under `adapt`. `bin/test/caddy-validate.sh` runs `validate` for helm's `SERVER_NAME=:80` and compose's `localhost, php.local:80, php.local:443` in the built image (unit-tests job, GitLab and GitHub; no php or database needed). Locally: `docker compose exec -T php sh -s < bin/test/caddy-validate.sh`. A Caddyfile under test must sit in `/etc/caddy/`, because of the relative `import worker.Caddyfile` in prod.

- **Single-file bind mounts truncate a longer replacement file** (#57): Caddy reports `unexpected EOF` / `unexpected token` on a file that's valid on disk. Fixed by reading the Caddyfile and entrypoint through the `./api:/app` directory mount (`entrypoint`/`command` in `compose.override.yaml`; keep `command` in sync with the `frankenphp_dev` CMD in `api/Dockerfile`). **If a parse error ever looks impossible, compare byte counts first:** `wc -c < api/frankenphp/Caddyfile` vs `docker compose exec php sh -c 'wc -c < /app/frankenphp/Caddyfile'`. A mismatch needs `docker compose up -d --force-recreate php`.
- **Quote characters in `#` comments are fine.** An old claim that they break Caddy was really the truncation.
- **⚠ CEL has no comment syntax.** A `#` line inside the backticks of `@use_cache expression` is a runtime error (`token recognition error at: '#'`, crash-looping php) that **`frankenphp adapt` reports as clean** (`validate` catches it). Keep commentary in Caddyfile comments above the block. After `adapt`, always `docker compose up -d --force-recreate php` and check it reaches `healthy`.
- `--watch` logs `unable to load latest config` on partial reads; usually noise. **Never judge a change by reading `/config/…` from the admin API** (it races the reload). Use `bin/test/caddy-validate.sh` (or `frankenphp validate`) and `docker compose restart php` before measuring.

### ⚠ `composer update` fails with a Flex recipes 404

`The ".../symfony/recipes-contrib/flex/main/index.json" file could not be downloaded (HTTP/2 404)` is a **stale GitHub PAT** in `/config/composer/auth.json`. GitHub returns 404, not 401, for a bad token, and an unauthenticated `curl` returns 200, so manual testing misleads. It persists because `/config` is a volume and the entrypoint only clears it when `vendor/` is empty. Fix: `docker compose exec php rm -f /config/composer/auth.json` (or set a valid `GITHUB_TOKEN`).

**CI composer installs authenticate with an optional `GITHUB_TOKEN`** (any fine-grained token, no permissions needed; GitHub Actions maps its own). `setup.sh` turns it into `COMPOSER_AUTH`, which test jobs use directly and `build_api` passes as the `composer_auth` build secret (never a build arg: it would land in the image history). Unset, it stays unset: an empty token is rejected outright, worse than anonymous. Anonymous installs get 60 requests an hour per IP and fail part way through on a shared runner. The build log's `github rate limit for this build:` line says 60 or 5000.

**`run_test_functional` unsets `MAILER_DSN` and `MAILER_EMAIL`:** every CI variable reaches the job and beats `api/.env.test`, so a project's live relay would deliver any email a test sends. Unset, tests get `.env.test`'s `MAILER_DSN=null://null` (built and assertable, never sent); without that line they'd fall back to `.env`'s `smtp-relay`, which CI doesn't have. Keep both halves when adding mail settings. It also unsets `JWT_SECRET_KEY`, `JWT_PUBLIC_KEY` and `JWT_PASSPHRASE` (#130): CI holds the key contents for the deploy, which `generate-keypair` would take as a path (failing, and printing the encrypted key in the log).

**The registry pull secret is `kubectl apply`d** (not `replace --force`, which raced when releases share a namespace). The first apply over a secret an older deploy created prints a one-off warning about a missing `last-applied-configuration` annotation. It's harmless; the secret is updated.

### Docker healthchecks (#205)

`docker compose up -d --wait` returns once the site is ready: php's `HEALTHCHECK` is `/_api/_/health` (php and the database), app's is `/_cwa/healthcheck` (Node only, never the API, so an API outage doesn't flap app). The database had one already.
- **php's goes through a loopback-only Caddy site, `http://127.0.0.1:2080`** (top of the Caddyfile: health paths only, `Host` rewritten to `BROWSER_SERVER_NAME`, which TRUSTED_HOSTS accepts wherever SSR works; no cache, no rate limit, no access log). **Don't point it at the main site:** no host is served over plain HTTP under every `SERVER_NAME` (compose `localhost, php.local:80, php.local:443`, e2e `localhost, php:80`, helm `:80`), and Caddy answers an unmatched Host with an empty 200, which `curl -f` passes.
- `start-period=300s` covers composer, migrations and `ANALYZE`; `start-interval=2s` makes `--wait` return within seconds of the first success (Docker Engine 25+). Failures then need 3 x 10s: a stopped database turns php unhealthy in ~30s and healthy again on the next check after it's back (measured in dev and worker mode).
- **Kubernetes ignores image healthchecks**; the chart's probes are unchanged. The scaled e2e `mercure` service runs the php image with its own `healthcheck:` (the hub Caddyfile has no 2080 site), and any other service that runs the php image with another Caddyfile needs the same.
- App's uses `wget` (busybox, in both node-alpine stages) on `127.0.0.1`, not `localhost` (can be `::1`). Dev's start period is 300s too, for `pnpm install`.

### Cold dev renders can 504

The first request to a page after a restart can exceed Souin's 30s backend timeout (`504`, `cache-status: … detail=DEADLINE-EXCEEDED`). Retry. A freshly restarted dev server also 504s under concurrency while Vite compiles.

## Caddy and Souin (`api/frankenphp/Caddyfile`)

- **Admin API is loopback-only.** `admin localhost:2019` with an `origins` list; port 2019 isn't published and helm has no `admin` containerPort. Admin rejects any Host not in `origins` with 403, even on loopback. Use it from inside the php container: `docker compose exec php curl -s http://localhost:2019/souin-api/souin` lists stored keys (`[]` = nothing cached). `CACHE_URL` in `api/.env` and helm's `cache-url` are `http://localhost:2019/…`. Flush everything: `curl -X PURGE http://localhost:2019/souin-api/souin/flush` in the php container or API pod.
- **Purging one page (#138):** never `PURGE <url>` on the site (405). Use `bin/console silverback:api-components:purge-http-cache --path /<path>` (or `--tag <tag>`; bundle 2.0.0-alpha.11), which goes through `SouinPurger` and so reaches Cloudflare too. By hand, through the admin API in the API pod, by tag: `curl -X PURGE -H 'Surrogate-Key: /_api/_/routes//<path>' http://localhost:2019/souin-api/souin` (204) drops the page from Souin and, with `provider cloudflare`, from Cloudflare. `-H 'Surrogate-Key: /<path>'` (Souin tags every entry with its path) clears Souin only, as does a regex purge (`/souin-api/souin/<regex>`). Nothing purges Cloudflare by URL; use its API (`purge_cache {"files":[…]}`).
- **`@use_cache` cookie clause.** `{http.request.cookie.api_component} == ""` does **not** match an absent cookie (a missing *header* does resolve to `""`; a missing cookie doesn't). The clause is `!{http.request.header.Cookie}.matches("api_component=[^;]+")`: cache when the cookie is absent or empty, never when it has a value. Its only job is to never cache an authenticated response; keep it fail-safe.
- **Cache host key (SSR and browsers share entries).** SSR calls the API on an internal host (`php.local`, or the in-cluster service), and `@internal` rewrites Host to `BROWSER_SERVER_NAME`, but `cache` runs before that. So the key uses `{http.vars.cwa_cache_host}`: `BROWSER_SERVER_NAME` for `/_api*`, `/uploads/*`, `/bundles/*` on a dotless or `.local` host, otherwise the request's Host.
- **At most three entries per page, whatever the browser sends (#79, #145).**
  - `order cache before encode`, and `Accept-Encoding` is normalised first (`@encoding_*` + `request_header`) to `br`, `gzip` or nothing, which is also in the key (`{http.vars.cwa_cache_encoding}`). So a hit is served already compressed, and each page is compressed once per encoding, on the miss. Before #145 the cache sat inside `encode` and every hit was recompressed: brotli capped a php pod at ~110 page views/s (measured locally: a cached 196 KB page cost ~4.4 ms CPU per br hit, ~1.0 ms after). zstd is dropped from `encode` (normalisation never asks for it). `bin/test/cache-encoding.sh` (unit-tests job, GitLab and GitHub) runs the real Caddyfile against a stub app and fails on the old order.
  - The otter store's 10,000-entry cap now holds up to three entries per page (and per `Accept` on `/_api`). A tag purge drops every variant.
  - `Accept` is in the key **for `/_api` only** (`@cache_accept` + `{http.vars.cwa_cache_accept}`; use the full `{http.vars.*}` form, `{vars.*}` isn't expanded in the global block).
  - **⚠ Don't "simplify" to dropping `Accept` from the key and relying on `Vary: Accept`.** API Platform's Swagger UI HTML sends no `Vary: Accept`, so JSON-LD requests got cached HTML. Also tried and failed: Souin per-path `cache_keys` (ignored when a global `template` is set, v1.7.9) and Caddy `map` (stored the literal placeholder).
- **Tracking parameters are stripped** (`uri @tracking_query query { -utm_source … }`), so `utm_*`, `gclid`, `fbclid`, `srsltid` etc. don't split the cache for pages or the API. Pages also go through the query allowlist (see *Origin protection*).
  - **⚠ It must run only when the query contains a listed parameter, and never for `/_nuxt/*`.** Caddy re-encodes the whole query whenever `uri query` runs (`?vue&…&lang.css` → `?vue=&…&lang.css=`), which made Vite serve every SFC style block as raw CSS labelled JS and broke `nuxt dev` (`Unexpected token '.'`, `Private field '#particles'`). If dev ever serves style blocks as raw CSS, compare Caddy against a direct request to Nuxt first.
  - **Keep the matcher expression's parameter list identical to the `-param` lines.** No wildcards; add a `-name` line per parameter. A project needing one server-side removes it from both.
  - Caddy's access log shows the **original** URI; a `utm_` there doesn't mean the strip failed.
- **Souin buffers a cacheable response's whole body in memory** before it decides anything; `max_cacheable_body_bytes` is checked only after buffering, so it can't protect memory. Large files must never match `@use_cache`. On the page branch only extensionless paths and `.xml` (the sitemap) match, so files in Nuxt's `public/` stream past the cache (#105: one 187 MB `brochure.pdf` download OOMKilled cymru-kitchens' API every time; locally a 200 MB file took php from 95 MB to 885 MB). **`{file.ext}` includes the dot** (`".pdf"`); the old `!= "pdf"` never matched.
- **The store (#170):** the Caddyfile's `{$CADDY_CACHE_STORAGE:otter}` line, so dev, e2e and every deploy use otter, capped at **10,000 entries by count, not bytes** (storages/otter v0.0.19 costs every entry 1). Another store is `CWA_API_CADDY_CACHE_STORAGE`. `CADDY_CACHE_EXTRA_CONFIG` is for other Souin directives only, empty by default and left out of the chart's Secret when unset; it used to hold the store (`k8s.sh` defaulted it to `otter`), so an override that added a setting silently dropped otter for Souin's unbounded `sync.Map` (which logs "default storage that is not optimized"). Dev still has no worker config, so don't read memory behaviour off the dev stack.
  - **Souin never refuses a duplicate:** `frankenphp validate` passes an extra store line (two stores found) and a second `timeout` block, which replaces the first entirely: `timeout { cache 1s }` alone puts the backend timeout back to Souin's 10s (measured). An unparseable duration is ignored the same way. So `check_cache_config` (in `deploy`, beside `check_cdn_config`) fails on an EXTRA_CONFIG line starting with a store name or `timeout`, and on a `CWA_API_CADDY_CACHE_BACKEND_TIMEOUT` that isn't a Go duration.
- **Backend timeout 30s (#170):** `timeout { backend {$CADDY_CACHE_BACKEND_TIMEOUT:30s} }`. Souin's own default, 10s, 504'd the first visitor of a cold CMS home page (~70 resources, ~12s to render on a 100m php pod) after every full flush and rollout, and Cloudflare passed the 504 on. 30s is 2.5x that render, equals the bundle warm's per-request `--timeout`, and stays under ingress-nginx's 60s and Cloudflare's 100s, so the origin answers first with Souin's own `DEADLINE-EXCEEDED`. It doesn't change load shedding (a request waiting for a php worker still gets a 503 at `FRANKENPHP_MAX_WAIT_TIME`); coalesced followers wait up to 30s holding a goroutine, not a worker, and with the singleflight patches a stall still costs one timeout and a 5xx is replayed, not stored. `bin/test/souin-backend-timeout.sh` (unit-tests job, GitLab and GitHub) checks a 12s render is served, stored once and coalesced, that the variable is read and that the store is otter; it fails on the old Caddyfile.
- **The app proxy retries a refused connection for 5 s** (`lb_try_duration 5s`, `lb_try_interval 250ms`, #216), so a restarting app container (single server) holds page requests instead of answering 502 at once. Only connection failures are retried, never a response, so on Kubernetes it adds at most 5 s to a request that finds no ready SSR pod. Measured on dev: app stopped, 502 after 5.2 s (was immediate); app started 1 s into the wait, the request was answered by app.
- **SSE must never be cached.** The Mercure exclusion is not optional: a cached SSE response never completes and connections pile up, which looks like the site falling over.
- **Purge separator.** `SouinPurger` hard-codes `', '`. API Platform's `xkey.glue` is only read by `VarnishXKeyPurger` (and is gone in API Platform 5). Check which purger class receives a parameter before assuming a mismatch.

### Origin protection (#106): query allowlist, rate limit, load shedding

Each new query string used to be a cache miss (a ~150ms SSR render, or one of 4 php workers), so `/?x=1`, `/?x=2`, … got past the cache. **Every setting is optional, with its default in the Caddyfile; none may become required** (Daniel, 2026-10-02). Caddy's `{$VAR:default}` uses the default only when the variable is **unset**: an empty value replaces it. So compose passes them through bare (`VAR:`, never `${VAR:-}`), and deploys set them as `CWA_API_<NAME>`, left out when empty.
- **`CACHE_QUERY_ALLOWLIST`** (default `page search order`; **never add `cwa_force`**: on an anonymous request a value other than `true` looped the module's navigation guard and pinned an SSR pod at 100% CPU, cwa-nuxt-module#366): pages keep only these parameters; `order` also keeps `order[...]`. `*` turns it off. **A site whose pages read another parameter must add it**, or SSR never sees it. Done by `query_allowlist`, the template's own Caddy handler (`api/frankenphp/caddy/queryallowlist`, built with `--with …=/tmp/queryallowlist`): Caddy can only delete parameters it's told the names of. It drops whole pairs, keeps the rest byte for byte (no re-encoding, unlike `uri query`), and is ordered after `uri`, before `cache`. Only on `@page_query`: extensionless, cacheable paths, the HTML branch's exclusions plus `/__*`, no auth cookie or header. **Keep `@page_query`'s exclusions in sync with `@use_cache`.** `/_api` keeps every parameter (resources declare their own, #89); it's left to the rate limit. The tracking denylist still runs everywhere except `/_nuxt/*`.
- **Rate limit** (`github.com/mholt/caddy-ratelimit`): `RATE_LIMIT_EVENTS` (3000) per `RATE_LIMIT_WINDOW` (`1m`) per visitor; `RATE_LIMIT_ENABLED=false` turns it off. `order rate_limit after cache`, so **cache hits are never counted**; misses and uncached paths are. 429 + `Retry-After`. Not limited: `/_nuxt/*`, `/.well-known/*`, and any private client address (SSR, the page-cache warm, probes, and the whole local dev stack, so test it with an `X-Forwarded-For` from a public address). The default is sized so the deploy's `warm_cache` (one CI runner, 3 at a time) can't trip it. A one-machine k6 `capacity`/`surge` run with `CACHE=cold` will: set `RATE_LIMIT_ENABLED=false` (`CWA_API_` on a deploy) for it.
- **⚠ The visitor's address, never a proxy's.** Keying on a proxy's address throttles every visitor behind it: a site-wide outage. `servers { trusted_proxies static {$CADDY_TRUSTED_PROXIES:private_ranges}; trusted_proxies_strict; client_ip_headers X-Forwarded-For }` makes `{client_ip}` the address that reached the ingress (right to left, so a prepended fake is ignored). Then `cwa_client_ip` is `CF-Connecting-IP` when `{client_ip}` is in Cloudflare's ranges (`(cloudflare_client)` snippet, `CLOUDFLARE_IP_RANGES` overrides the built-in list; the header is believed from nowhere else); `{client_ip} {X-Forwarded-For}` from an untrusted public peer that sends X-Forwarded-For (an unknown CDN or load balancer: each visitor still counts separately, but a client can dodge the limit with invented headers; add the proxy's ranges to `CADDY_TRUSTED_PROXIES`, e.g. a Google load balancer's `35.191.0.0/16 130.211.0.0/22`); otherwise `{client_ip}`. **`CADDY_EDGE=true`** (Caddy faces the internet; `compose.prod.yaml` defaults it to `true`, everything else to `false`) turns the middle case off, so a direct client is counted by its own address and invented `X-Forwarded-For` values can't dodge the limit; Cloudflare is still recognised. Complementary matchers, like `cwa_cache_host`. A site setting `servers` options in `CADDY_GLOBAL_CONFIG` must merge them into the Caddyfile's block. **The ingress must keep the client address (#135):** with `externalTrafficPolicy: Cluster`, nginx sees node IPs (private), every visitor looks internal and the limit never applies. The GKE cluster's controller (helm release `ingress`, `gitlab-managed-apps`) runs `Local` with 2 replicas, anti-affinity and a PDB since 2026-10-10; behind Cloudflare `client_ip` is then an edge address and `visitor_ip` the visitor. A new cluster needs the same; check `visitor_ip` in php's access log.
  - **Only Caddy knows the visitor (#111).** `cwa_client_ip` keys the rate limit and is logged as `visitor_ip` (`log_append`); the access log's own `client_ip`, and Symfony's `getClientIp()`, are still Cloudflare's address behind Cloudflare. Nothing in the template or bundle keys on the client IP today; site code that needs it must not trust `getClientIp()` there. `PURGE`/`BAN` through the site get a 405 (#138); the app's own purges use the loopback admin API (`localhost:2019`).
- **`FRANKENPHP_MAX_WAIT_TIME`** (default `5s`, `0` = off), in `worker.Caddyfile` (so prod only; dev has no worker config). FrankenPHP accepts `max_wait_time` only in the global `frankenphp` block, which `worker.Caddyfile` is imported into. A request that waits that long for a thread gets a **503** instead of queueing into Souin's 30s 504. Probes: a probe that can't get a worker fails at 5s either way (their timeout); liveness needs 6 consecutive failures, so a flood the pod is surviving doesn't restart it unless every probe for a minute is shed.
- **Optional ingress-nginx limits:** `CWA_CI_INGRESS_RATE_LIMIT_RPS` (off unless set), `CWA_CI_INGRESS_RATE_LIMIT_BURST_MULTIPLIER`, `CWA_CI_INGRESS_RATE_LIMIT_CONNECTIONS` → `ingress_rate_limit_annotations` in `k8s.sh`. They count every request, hits and `/_nuxt` included, by the address that reached nginx: far higher numbers than Caddy's, and **never behind Cloudflare** unless the controller reads the real IP itself.
- **⚠ The Caddyfile now needs the rebuilt php image** (`query_allowlist`, `rate_limit`). An old image fails with `unrecognized directive` (the dev `--watch` reload keeps the old config; a restart crash-loops). After pulling: `docker compose build php && docker compose up -d php`.
- Test it in a throwaway container: the dev stack's browser traffic may arrive from a private address (exempt) or, on some Docker Desktop setups, a public-looking one (counted). `frankenphp adapt` checks syntax only (`validate` provisions); the handler order to expect is `rewrite → query_allowlist → cache → rate_limit → encode` (`request_header` adapts to a `headers` handler near the top).
- Open: a request with `Cache-Control: no-cache` always misses Souin (measured: `fwd=uri-miss; stored` every time), so it's a second cache bypass the allowlist doesn't close. The rate limit counts it.
- Not done: alerting (needs `gcloud` and a GCP identity the deploy job doesn't have; see #106).

### ⚠ Patched Souin build (#84)

Souin v1.7.9 deletes purged tags' index entries with an **unanchored regex**, so purging a tag orphans every tag that contains it (every write to one component group or position orphaned all the others; routes where one path contains another). Orphaned entries are then unpurgeable for the full prod `s-maxage` (a year). Upstream: darkweak/souin#867, fix PR #868.
- `api/frankenphp/souin/v1.7.9-purge-fix.patch` (and `v1.7.9-singleflight-fix.patch`, see *php probes*, plus the singleflight 5xx, flush and Cloudflare patches below) + the builder-stage `COPY`/`RUN` in `api/Dockerfile` + `--with github.com/darkweak/souin=/tmp/souin`. **Remove all three together** once a Souin release has the fix; downstream sites get the change through the next release's `cwa-php-base` (see *Published php base*).
- `bin/test/souin-purge-isolation.sh` (in the unit-tests job on GitLab and GitHub) fails on the unpatched binary. Run it locally without an image build: `docker compose exec -T php sh -s < bin/test/souin-purge-isolation.sh`.
- A site upgrading to the patched image whose API pod wasn't recreated needs one full flush.
- Downstream copies must build the same Souin version (`frankenphp build-info | grep souin`), or the patch fails loudly.
- **Third patch: `v1.7.9-cloudflare-purge.patch` (#108).** Souin's Cloudflare purge never worked: it POSTs to `/zones/<id>/purge` (not `/purge_cache`), sends only Global API Key headers, and discards the result in a goroutine, so it fails silently with any credential. The patch fixes the endpoint, sends `api_key` as `Authorization: Bearer` when `email` is empty (a scoped Zone → Cache Purge token), puts a 30s timeout on each request and logs any failure. Only active with `provider cloudflare` in `CADDY_CACHE_CDN_CONFIG`; setting that variable replaces the whole default, so repeat `strategy hard` in it. **Souin panics on a `cdn` line with no value** (`index out of range`, php crash-loops, helm still says deployed), e.g. `api_key` after a GitLab variable that is Protected on an unprotected branch expanded to nothing. `check_cdn_config` (first thing in `deploy`) fails the job on that, or on an unexpanded `$NAME` (#116). Souin itself is unpatched there (a second module, `plugins/caddy`), so local compose still panics.
- **Cloudflare purges are paced, not sent straight out (#115).** Cloudflare limits purge requests **per account**, all kinds sharing one allowance (Free: 5/min, burst 25), and answers `429` beyond it. The patch queues purges in one sender per zone (shared across config reloads), deduplicates tags, sends up to 100 per request through a token bucket, retries `429` (after `Retry-After`), `5xx` and network errors, and drops other failures (a bad token) with a log line. A backlog it can't send within a minute becomes one purge everything; a flush replaces anything queued. `CLOUDFLARE_PURGE_PLAN` (`free` default, `pro`, `business`, `enterprise`), overridden by `CLOUDFLARE_PURGE_REQUESTS` per `CLOUDFLARE_PURGE_WINDOW` (Go duration) and `CLOUDFLARE_PURGE_BURST`; optional, set like the origin-protection settings (`CWA_API_CLOUDFLARE_PURGE_*` on deploys). Each process has its own bucket, so staging and production (or several sites) on one account should set a lower rate. The queue is in memory: a crash loses pending edge purges (a deploy purges everything anyway). Go tests live in the patch (`cloudflare_purger_test.go`, fake clock + stub server); the binary can't be pointed at a stub, so no shell test.
- **Every purge reaches Cloudflare.** Tag purges (writes via `SouinPurger`, `purge-rendered-html`) purge those tags; a full flush (`/flush`: "Purge all cached data", `purge-http-cache`, every fixture load) purges **everything** in the zone, through a `Flush()` override the patch adds to the Cloudflare provider (Souin calls `Flush()` only on `/flush`; the Cloudflare patch applies after the flush patch below and depends on it). `dynamic` in the `cdn` block is never read in v1.7.9.
- **Fourth patch: `v1.7.9-flush-no-close.patch` (#114).** Souin's `/flush` called the surrogate storage's `Destruct()`, i.e. the storer's `Reset()`, which **closes** Badger and Nuts (and go-redis, etcd, Olric); only otter's clears. After any full flush nothing was cached until php restarted (`BADGER-INSERTION-ERROR`, `DB Closed` in the log). The patch adds `Flush()` to Souin's `SurrogateInterface` (deletes `^SURROGATE_` keys, keeps the storer open) and the flush calls that; `Destruct()` stays for shutdown. `bin/test/souin-flush-storage.sh` (unit-tests job, GitLab and GitHub) flushes otter, badger and nuts and checks each stores and hits again; it fails on the unpatched binary. Upstream: a Souin issue + PR drafted, not yet filed. Remove with the others once a Souin release has it (then rebase the Cloudflare patch onto `Flush()`).
- **Fifth patch: `v1.7.9-singleflight-5xx.patch` (#137)**, applied straight after the singleflight fix. Upstream bug, present in Souin master too: when the coalesced leader got a 500/502/503/504, `Upstream` returned `nil, Upstream50xError` from the singleflight callback, so followers had nothing to write and `ServeHTTP` sent their untouched writer: **200, empty body, no `Cache-Status`** (an SSR render could then cache a broken page). Followers now replay the leader's status, headers and body; a private or `Set-Cookie` 5xx sends each follower upstream itself, as for a 2xx. Go tests in the patch (`singleflight_5xx_test.go`); `bin/test/souin-coalesced-5xx.sh` (unit-tests job, GitLab and GitHub; slow `php -S` upstream) fails on the unpatched binary. Upstream issue + PR drafted, not filed.
- **Sixth patch: `v1.7.9-writer-flush.patch` (#185).** Souin's `CustomWriter` (`pkg/middleware/writer.go`) has no `Flush` or `Unwrap`, so a PHP `flush()` behind `cache` logs FrankenPHP's `WARN the current responseWriter is not a flusher … {"error": "feature not supported"}`. In dev that's every `/_api` miss (with `APP_DEBUG`, Symfony's `HttpKernelRunner` calls `flush()` instead of `fastcgi_finish_request()`); in prod (worker mode, `fastcgi_finish_request()`) only a `StreamedResponse`, e.g. the bundle's file downloads. Noise, nothing lost: Souin buffers the whole body anyway (a PHP `flush()` behind `cache` reaches the client only at the end, with or without the patch), and the template sends no Early Hints. The patch adds a no-op `Flush()` (as Caddy's buffering `ResponseRecorder` does); never make it flush or unwrap to the real writer, which would send headers before `Cache-Status` and the store decision. `bin/test/souin-php-flush.sh` (unit-tests job, GitLab and GitHub) fails on the unpatched binary. The warning on an *uncached* path would be a different handler. Upstream issue drafted, not filed.
- **Storages patch: `api/frankenphp/storages/go-redis-v0.0.20-atomic-sets.patch` (#85)**, darkweak/storages#65's go-redis half (filed upstream, with darkweak/souin#870). The image builds `go-redis/caddy` (Redis store, used only in scaled mode) with `--with github.com/darkweak/storages/go-redis=/tmp/storages-go-redis`. Unpatched, two pods sharing Redis lose members of a shared tag set (a read-then-write update) and v0.0.20's hash mappings break Souin's purge (`WRONGTYPE`): pages stay cached after their tag is purged. The replace also stops `go-redis/caddy` v0.0.20 resolving the base at v0.0.19. `bin/test/souin-redis-shared-purge.sh` (unit-tests job with a `redis:8.10.2` service, GitLab and GitHub; `REDIS_ADDR`, default `redis:6379`) runs two instances on one Redis and fails on the unpatched module (measured: 186, 45, 73 of 200 pages left). Remove the patch, its `COPY`/`RUN` and the replace once a storages release has #65. Only one of `go-redis/caddy` and `redis/caddy` can be built.
- **`Cache-Tag` comes from the Caddyfile, not Souin:** Souin never puts it on a response, hit or miss. A `header { >Cache-Tag {http.response.header.Surrogate-Key} }` block after `cache` copies it, so Cloudflare can purge by tag. Don't remove it if edge caching is in use. **Only on public hosts (#118):** the `@cache_tag` matcher skips dotless/`.local` hosts (SSR's), because doubling the tag headers took `/_api/_/routes` past Node's 16 KB header limit (`UND_ERR_HEADERS_OVERFLOW`, empty sitemap). `Surrogate-Key` alone still grows per resource (~230 routes = 16 KB), so the app image sets `NODE_OPTIONS=--max-http-header-size=65536`; a deploy that sets its own `NODE_OPTIONS` must keep the flag. Long term: a grouping key (api-components-bundle#227).
- **⚠ Cloudflare ignores `Vary` (except `Accept-Encoding`), and Free can't key on a request header.** The Cloudflare API rule therefore matches only the module's exact `Accept` values (for `Vary: Accept`) and **must exclude `/_api/_/component_positions/`**: a position bound to page data returns a different component per page, chosen by the `path` request header (`Vary: path`, the bundle's `ComponentPositionEventListener`). Without the exclusion, every page-data page showed the first cached page's content after client-side navigation, for a year (found on preview.cwa.rocks, 2026-10-05; docs#134). Souin keys on `Vary` correctly. Any new API response that varies on a request header needs the same exclusion. After changing the rule, purge everything once.

### Caddy build pins

- **Nothing is pinned** (Mercure unpinned in #67, once `dunglas/frankenphp:builder` 1.13.0 shipped Go 1.27). The plugins follow their latest releases, which follow the builder's FrankenPHP: **a plugin can't be pinned below a version FrankenPHP itself requires.** Pinning `mercure/caddy@v0.24.2` under FrankenPHP 1.13 (which requires Mercure 1.0.3) made Go downgrade `frankenphp/caddy` to 1.12.7 and the build failed with `undefined: mercure.WithPublisherJWT`. If a plugin release needs a newer Go than the builder has (`requires go >= 1.27 (running go 1.26.8; GOTOOLCHAIN=local)`; Vulcain 1.4.4 did on 2026-10-02), check for a newer builder image before pinning anything.
- **Mercure 1.0, modern mode (#67, bundle 2.0.0-alpha.8 / api-components-bundle#377, module #364).** Tokens are OAuth 2.0 access tokens (`typ: at+jwt`, `iss`, `aud`, `exp`, `authorization_details`); subscribers use `match=` (a `topic=` subscription is `400`); the cookie is `__Secure-mercure_access_token`, pinned as `cookie_name` in `mercure.yaml` because mercure-bundle 0.6 drops the `__Secure-` prefix when `kernel.debug` is on, which the hub wouldn't read. Three settings must agree:
  - **`iss`:** fixed to `cwa` in both `jwt.claims.iss` (`mercure.yaml`) and the Caddyfile's `issuer cwa` block. Deliberately not a variable (#110): Caddy reads only the process environment while Symfony also reads `api/.env*`, so a variable set in one place would change one side and make every token `401`. Change both together or neither.
  - **`aud`:** mercure-bundle sets it to `public_url` (`MERCURE_PUBLIC_URL`), and the Caddyfile pins `resource_identifier` to the same variable. **Don't remove the pin:** the API publishes through the internal URL, and an unpinned hub expects the URL each request arrived on, so every publish would be `401`.
  - **Grants:** the bundle's URL Patterns end in `\?` (published only) or `\?draft=1` (drafts). Without the explicit query, `…/:id` also matched `?draft=1`.
  - `caddy adapt` checks none of this. `validate` (`bin/test/caddy-validate.sh`) catches provisioning errors; tokens still only fail on a running hub. To test without rebuilding, run `dunglas/mercure:v<same version>` on the compose network with the Caddyfile's `mercure` block, mint the publisher token from `test.service_container` (`mercure.hub.default` → `getProvider()->getJwt()`) and take the subscriber cookie from an anonymous `/_api/me`. Verified on 2026-10-04: public updates reach everyone, private ones reach cookie holders, drafts nobody anonymous.
  - Compatibility mode (`protocol_version_compatibility 8` plus the `deprecated_topic,deprecated_claim` build tags) was the bridge before the bundle and module moved; don't bring it back. Read [Mercure's upgrade guide](https://github.com/dunglas/mercure/blob/main/docs/UPGRADE.md) and release notes before any Mercure change.
- **The hub is named (`name cwa`, #113).** Mercure ≥ 1.0.3 allows one *unnamed* hub per Caddy HTTP app, and a `SERVER_NAME` with several ports (compose's `localhost, php.local:80, php.local:443`) makes one server per port, each provisioning the `mercure` block: php crash-looped with `only one unnamed Mercure hub is allowed per configuration` (helm's `:80` has one server, so deploys were fine). Copies with the **same** name share one pooled transport (keyed by transport config + hub name), so the API's publish on `php.local:80` reaches browsers on `:443`. Don't give the copies different names, or publishes stop reaching subscribers. Tested with `dunglas/mercure:v1.0.4` (two ports) and the compose stack.
- **Mercure 1.0 rejects unknown directives** (`unknown mercure directive`) and removed `demo` and `ui`: use `debugger` (dev's `MERCURE_EXTRA_DIRECTIVES`) or `playground` (insecure, creates an all-access token; never in production). The value after `transport bolt` is ignored, in 0.x and 1.0 alike: the database is always `/data/caddy/mercure.db` (`transport bolt { path … }` sets it).
- Comment lines inside a `RUN` continuation are safe (BuildKit strips them).

### Published php base (#208)

`ghcr.io/components-web-app/cwa-php-base` is `api/Dockerfile`'s `cwa_php_base` stage: the patched FrankenPHP (builder stage: Souin and storages patches, `queryallowlist`, xcaddy plugins), apt packages, `retry-fetch`, the PHP extensions (`pdo_pgsql` included; `xdebug` built but disabled, `frankenphp_dev` runs `docker-php-ext-enable xdebug`) and the vips env. **No project file goes in it** (Caddyfile, `conf.d`, entrypoint): `bin/test/php-base-version.sh` fails on any `COPY` there but the binary and `retry-fetch`.
- **`frankenphp_base` is `FROM ${CWA_PHP_BASE}`.** From the first release with #208, the ARG defaults to `cwa-php-base:<this release>`, so downstream builds pull it and compile no Go (#213) and install no extensions (#176). `cwa_php_base` names the stage and builds it from source instead; BuildKit skips `builder` and `cwa_php_base` otherwise. The legacy builder (`DOCKER_BUILDKIT=0`) can't do this.
- **The first release with the image was 2.0.0-alpha.44.** Each release commit sets `ARG CWA_PHP_BASE=ghcr.io/components-web-app/cwa-php-base:<that version>` with create-cwa's version (`php-base-version.sh` fails otherwise), so `main`'s default names the last release, whose image exists.
- **`build_api`'s base (`php_base_build_args`):** `CWA_CI_PHP_IMAGE_FROM_SOURCE="true"` builds from source; else `CWA_CI_PHP_BASE_IMAGE` (a rebuild tag, or `X@sha256:…`) is passed as the build arg, so a site takes a rebuild without editing the tracked Dockerfile; else **the template's own pipelines build from source** (matched by `CI_PROJECT_PATH`/`GITHUB_REPOSITORY`, so it never applies downstream; `CWA_CI_PHP_IMAGE_FROM_SOURCE="false"` turns it off), so the patches are tested on every push (the unit tests run in that image); else the Dockerfile's default. No GitLab variable is needed for the template. A downstream project that changes the patches, `queryallowlist` or the plugins sets `CWA_CI_PHP_IMAGE_FROM_SOURCE="true"`, not Protected (unprotected review branches would pull the release's binary).
- **Freshness changed:** a from-source build pulled a fresh `dunglas/frankenphp:latest` (PHP patch releases, Debian security fixes) every time; a pulling project is frozen at its release's base until it takes a newer release or sets `CWA_CI_PHP_BASE_IMAGE` to an `X-rYYYYMMDD` rebuild. Only the newest release is rebuilt, and a rebuild can move to a new PHP minor if `dunglas/frankenphp:latest` has.
- **Local dev** uses the Dockerfile's default. `compose.override.yaml` and `compose.prod.yaml` pass `CWA_PHP_BASE` only when set (compose drops a valueless `args` entry); a maintainer changing patches sets `CWA_PHP_BASE=cwa_php_base` in the root `.env` (commented in `.env.dist`). Never set it to an empty value: `FROM ""` fails.
- **Downstream takes #208 at the release tag, not from `main` commits**, and a release commit's default exists only once its tag's workflow has published it (~30 min; the template's CI doesn't care).
- **Version tags are never overwritten** (GHCR has no immutability setting): `X` from template tag `vX`; `X-rYYYYMMDD` from the Monday 04:17 UTC rebuild of the newest release that has the stage, or the same rebuild run by hand for a security release (`gh workflow run publish-php-base.yml --ref main -f ref=main -f tag=rebuild`; attested like the scheduled one, no template tag needed; downstream sites take it through `CWA_CI_PHP_BASE_IMAGE`); `test-<name>` from a manual run (`gh workflow run publish-php-base.yml -f ref=<ref> -f tag=test-<name>`). **`latest` is the one moving tag** (Daniel, 2026-10-21): `merge` copies the attested index to it after each release or rebuild, never a test, and never to an older version than its own `org.opencontainers.image.version` (`sort -V`), so a rerun of an old release can't move it back. Same digest and attestation as the version tag. For trying the image by hand only: Dockerfiles and `CWA_CI_PHP_BASE_IMAGE` keep naming a version. `plan` and `merge` check with `.github/php-base/ghcr-tag-state.sh`: logged in, 200 is present, 404 absent (a package not created yet is a 404 too), anything else fails the run, so a registry error can't read as absent.
- **`publish-php-base.yml`:** each architecture (amd64, native arm64) is built with `no-cache`, `pull`, `provenance: mode=max` and an SBOM, pushed by digest only, and smoke-tested on its own runner with the checkout mounted read-only (`bin/test/php-base-smoke.sh`: the replaces in `build-info`, the extensions, then the Souin and Caddyfile tests). Only then does `merge` tag the multi-arch index. **Every checkout has `persist-credentials: false`:** the smoke test runs the built binary (unpinned upstream plugins) beside a `packages: write` token. The image config's OCI labels (source, revision, version, title, `licenses=NOASSERTION`: PHP, Caddy, libvips and Debian packages keep their own licences, see the SBOM) replace the ones inherited from `dunglas/frankenphp`, **and project images inherit them**; the index carries the same as annotations. On a release tag, `verify-default` builds `frankenphp_prod` with no build arg and validates its Caddyfile. A failed test leaves an untagged digest and no tag. Excluded from generated projects (with `.github/php-base/`), and guarded by `github.repository`.
- **Attestations: releases and rebuilds only.** A `test-*` build of any ref isn't attested, so it can't verify like a release. Verify a release with `gh attestation verify oci://ghcr.io/components-web-app/cwa-php-base:X --repo components-web-app/components-web-app --signer-workflow components-web-app/components-web-app/.github/workflows/publish-php-base.yml --source-ref refs/tags/vX` (a rebuild's source ref is `refs/heads/main`); `merge` runs the same check, and the command and digest go in the release notes (step 4).
- **A change on `main` that needs a new plugin or patch** (e.g. a Caddyfile directive) breaks `--ref main` installs and downstream pull builds of `main` until the next release: release soon after one.
- Projects can pin `cwa-php-base:X@sha256:…` through `CWA_CI_PHP_BASE_IMAGE`; the Dockerfile default can't carry a digest, which isn't known at the release commit.

## Page cache

The module renders cacheable pages with `Surrogate-Key: cwa-html, <every resource IRI it rendered from>` and owns `Cache-Control` through its own Nitro hook. The bundle purges those keys on write. The template sets **no** page-cache config.
- A component write drops exactly the pages that rendered it; a `SiteConfigParameter` write drops every page via `cwa-html` (the bundle's `purge_rendered_html_classes` default).
- **`cwa-html` is a cross-repo contract**: `RENDERED_HTML_SURROGATE_KEY` in the module, `HttpCachePurger::RENDERED_HTML_TAG` in the bundle. A mismatch fails silently.
- **Lifetime follows the API:** pages take the lowest `s-maxage`/`Expires` of the render's API responses (module #325), falling back to 3600 only if none gave one. The API's `shared_max_age` is **60 in dev** and **31557600 (a year) in prod** (`config/packages/prod/api_platform.yaml`). Both are intended; invalidation is purge-driven. `staleWhileRevalidate` stays 0 deliberately.
- **The dev TTL masks purge bugs**: a page looks invalidated within a minute even if nothing purged it. Measure `cache-status` immediately before and after the write.
- **Exclusions** (no `cache-status` header at all): `/login`, `/forgot-password`, `/reset-password/*` (one entry per token otherwise), `/verify-email`, `/confirm-new-email` (the bundle emails tokenised links there even though the module has no pages yet), `/user-area`, `/_cwa/healthcheck`, `/.well-known/mercure`, `/_api/me`, `/_api/logout`, and anything with `api_component=<value>` or `Authorization`. On the page branch, any path with a file extension other than `.xml` (static files from Nuxt's `public/`), and `.pdf` under `/_api`. **When the module adds or renames an auth page, update this matcher** (module pages: `@cwa/nuxt`'s `dist/runtime/templates/pages/`).
- **Error pages are never stored** (module #340): a 404 goes out `private, no-store` with no `Surrogate-Key`, so a scheduled route is 200 as soon as its `liveAt` passes. If a scheduled route is still 404 after its time and `cache-status` shows a Souin `hit`, that's a regression.
- A 404 on a draft nested component no longer makes the page uncacheable (module #324), and its IRI stays in the page's `Surrogate-Key`, so publishing it purges the page.
- **Admin purge buttons:** site settings → purge page cache (`POST /_/rendered_html/purge`) and "Purge all cached data" (`POST /_/http_cache/purge` with no body); "Purge this page" (module alpha.20) sends the same endpoint `{"paths": [...]}` and drops only that page's tags (bundle alpha.25; any other body is a 422). CLI: `silverback:api-components:purge-rendered-html` (pages only) and `silverback:api-components:purge-http-cache` (everything).
- The sitemap is sent with `Surrogate-Key: cwa-html, /_api/_/routes`, so route writes and the deploy purge drop it.

## Deploy and Kubernetes

### Deploy defaults: don't set what the template already decides (2026-10-08)

Projects used to set the same CI variables by hand (Daniel: a copy of the template shouldn't need them). `apply_site_defaults` (first thing in `deploy`, after `check_cdn_config`) now fills them, and a CI variable still wins:
- `CWA_CI_INGRESS_ENABLED` `true`. **`CWA_CI_CLUSTER_ISSUER` is not defaulted to production (Daniel, 2026-10-08):** `setup.sh` makes an unset one `letsencrypt-staging`, so each production site opts in with `CWA_CI_CLUSTER_ISSUER=letsencrypt-prod` once its domain points at the cluster, and a misconfigured domain fails against the staging issuer's far higher limits. An explicit empty value turns cert-manager off. (alpha.11 and alpha.12 briefly defaulted it to production; #119.) Test defaults through the real chain (`source setup.sh; source k8s.sh`), not `k8s.sh` alone.
- `CORS_ALLOW_ORIGIN` `^https://(?:<hosts>)$`, `TRUSTED_HOSTS` `^(?:<hosts>|localhost)$`, `MERCURE_CORS_ORIGIN` `https://<host> …`, from `site_hosts`: `DOMAIN` plus `KUBE_INGRESS_ALIAS_DOMAINS` on the stable track. Exact hosts, so review apps and staging get their own (a `*`-scoped value used to give staging production's Mercure origin).
- `DATABASE_SSL_MODE` `require` when `CWA_CI_POSTGRES_ENABLED=false` (an external database); the in-cluster PostgreSQL keeps `prefer`.
- An unset `CADDY_CACHE_CDN_CONFIG` now reaches no env var at all (secret key written only when set, `optional: true`), so the Caddyfile's `strategy hard` applies. **Before this, unset meant a newline** (`echo "" | base64` = `Cg==`), which replaced that default with an empty `cdn` block, and Souin then keeps stale copies on purge (`keepStale = strategy != "hard"`). That's why every project set `strategy hard`.
- Already defaults, never worth setting: `CWA_CI_API_REPLICA_COUNT=1`, `CWA_CI_BUILD_DISABLED`/`CWA_CI_TEST_DISABLED=false`, `CWA_CI_FIXTURES_ENABLED=false`, `CWA_CI_RESET_DATABASE=false`, `CWA_CI_WWW_REDIRECT=false`, `ADMIN_USERNAME=admin`, `CWA_CI_PWA_AUTOSCALE_MIN` (production 2, other tracks 1), `KUBERNETES_VERSION` (1.31.0), `HELM_VERSION` (3.19.0).
- **In-cluster PostgreSQL credentials** are `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` (as in compose and the test jobs), written to `postgresql.global.postgresql.auth` only when set; `secrets.yaml` builds `database-url` from the same values, percent-encoded. Unset keeps `values.yaml`'s `example` / `!ChangeMe!` / `api`. Set a real `POSTGRES_PASSWORD`.
  - **⚠ Bitnami applies credentials only on first init.** Without persistence, a user or database change restarts the pod empty; a password-only change doesn't restart it, so the API can't connect until `kubectl delete pod <release>-postgresql-0`. With persistence, the volume keeps its original credentials: change them in `psql -U postgres` first (`ALTER USER`/`ALTER DATABASE`; a rename clears the password), then deploy.
  - **Persistence:** `CWA_CI_POSTGRES_PERSISTENCE` (`true`/`false`), `_PERSISTENCE_SIZE` (`1Gi`), `CWA_CI_POSTGRES_STORAGE_CLASS` (`standard`, `-` for none); unset keeps the chart's (off).
  - **`volumeClaimTemplates` are immutable:** `check_postgres_persistence` stops the deploy before helm when the switches differ from the live StatefulSet and prints the fix (`kubectl delete statefulset <release>-postgresql --cascade=orphan`, then deploy). Nothing is deleted automatically.
  - `delete review` also deletes the release's PostgreSQL PVCs. Other tracks keep theirs: a persistent staging or canary volume outlives `delete staging`/`delete canary` (drop it with `kubectl delete pvc data-<release>-staging-postgresql-0`), and a production-scoped `CWA_CI_POSTGRES_PERSISTENCE` reaches staging on GitLab.
- **GitLab scope trap:** the staging job runs under `environment: production`, so a `production`-scoped variable reaches staging too. Per-track sizing belongs in `k8s.sh`'s track defaults, not in an environment-scoped variable.

### CI settings are `CWA_CI_*` (2026-10-09)

The template's own switches and deploy tuning are `CWA_CI_<NAME>`; the old names (table in `CHANGELOG.md`, 2026-10-09) are not read, with no fallback or warning (alpha). A new template setting gets a `CWA_CI_` name, or no wiring at all if it's php runtime config (`CWA_API_`). Not renamed: platform names (`CI_*`, `KUBE_*`, `RELEASE_PRODUCTION`, `KUBECONFIG`, `GITHUB_TOKEN`, `KUBERNETES_VERSION`, `HELM_VERSION`), site values and secrets, `CWA_ENVIRONMENT`, and every name inside the containers and compose.
- **GitLab:** a bare `$VAR` inside `&&`/`||` is true even when empty; compare with `null`/`""`. Test rules with `glab ci lint --dry-run` on a copy whose switch names are swapped for unused ones, or the project's own CI variables leak in.

### Site settings: `NUXT_*` and `CWA_API_*` passthrough (#125)

**Site settings are runtime env vars, never Docker build args** (`runtimeConfig`, `%env()%`): images are built once for every track. Never add a `--build-arg`/`--secret` for one.
- `site_env_values` (in `deploy`) passes every `NUXT_PUBLIC_*` CI variable to the PWA's ConfigMap, every other `NUXT_*` to its Secret, and `CWA_API_<NAME>` to the API's (and orphan scan's) Secret as `<NAME>`, through `envFrom`. A new setting needs no template edit.
- **An empty `CWA_API_` value is left out** (it would replace a Caddyfile `{$VAR:default}` or Symfony default); an empty `NUXT_*` is passed on (Nuxt applies it).
- **The API's optional runtime settings are only `CWA_API_*`:** `CACHE_QUERY_ALLOWLIST`, `CADDY_TRUSTED_PROXIES`, `CLOUDFLARE_IP_RANGES`, `RATE_LIMIT_*`, `FRANKENPHP_MAX_WAIT_TIME`, `CADDY_CACHE_STORAGE`, `CADDY_CACHE_BACKEND_TIMEOUT`, `CLOUDFLARE_PURGE_*`, `CADDY_GLOBAL_CONFIG`, `JWT_COOKIE_SAMESITE`, `MERCURE_JWT_ALGORITHM`, `WEBSITE_NAME` (the bundle's `website_name`, used in emails; `api/.env` defaults it to `New Website`), and any other php env. No chart wiring. Not the worker count or `memory_limit`: those are the memory budget's `CWA_CI_API_*` (see *Media and uploads*).
- **Explicit on purpose:** `CORS_ALLOW_ORIGIN`, `TRUSTED_HOSTS`, `MERCURE_CORS_ORIGIN`, `DATABASE_SSL_MODE` (computed by `apply_site_defaults`; the CI variable overrides) and `CADDY_CACHE_CDN_CONFIG`/`_EXTRA_CONFIG` (validated, base64; the reserved-name error for a `CWA_API_` copy names the plain CI variable).
- **The deploy fails before touching the cluster** on a reserved name (`SITE_ENV_RESERVED_API`/`_PWA`: the chart's explicit `env:` would win) or an unusable one. **Adding an explicit `env:` entry to the chart means adding its name to the reserved list.** A project must delete any `NUXT_CWA_API_URL`, `NUXT_PUBLIC_CWA_API_URL(_BROWSER)`, `NUXT_SITE_URL` or `NUXT_PUBLIC_CWA_ENVIRONMENT` CI variable.
- **`NUXT_SITE_URL` is `https://$DOMAIN` on every deploy (#140)**, so canonical URLs and `og:url` in cached pages never take the host of whichever request rendered them (nuxt-site-config reads `NUXT_SITE_*` at runtime).
- **`CWA_ENVIRONMENT` / `NUXT_PUBLIC_CWA_ENVIRONMENT`** come from the track (`production`, `staging`, `canary`, `review`), not GitLab's environment. A `CWA_ENVIRONMENT` CI variable overrides it.
- **GitHub:** `github-export-secrets.sh` exports `NUXT_*`/`CWA_API_*` secrets, masked, in deploy jobs only, after the setup actions.

### Project hooks: keep `setup.sh` and `k8s.sh` the template's (2026-10-10)

Projects copy `bin/devops/setup.sh`, `k8s.sh` and the chart, and cwa-deployment-statuses tracks them by exact content, so a project that edits them can't take later releases as plain file copies. Project-specific deploy logic goes in **`bin/devops/project.sh`** (optional; `setup.sh` sources it in every job), never in the template's files:
- It can set `DOMAIN` (e.g. which of several sites a job deploys); `setup.sh` falls back to the environment url's host, and `check_kube_domain`, `persist_environment_url`, `warm_cache` and `performance_audit` work from `DOMAIN` (#132; CI passes the last two no URL). `persist_environment_url` also writes `environment_url.env` (`SITE_ENVIRONMENT_URL`) for a job whose url is worked out in the job. The template's `environment: url:` stays static (`setup.sh` reads `CI_ENVIRONMENT_URL`); a project that sets `DOMAIN` can point its deploy job's url at `$SITE_ENVIRONMENT_URL` with `artifacts: reports: dotenv: environment_url.env`.
- **No `test-domain.com` fallback (#134):** with no `DOMAIN` and no environment url (builds, tests) `DOMAIN` is empty, and `check_kube_domain` fails on an empty one or one with a leading or trailing dot (an empty `KUBE_INGRESS_BASE_DOMAIN` in the url).
- It can export site settings for the passthrough (`CWA_API_*`, `NUXT_*`), add names its own chart `env:` entries set to `SITE_ENV_RESERVED_API_EXTRA` / `SITE_ENV_RESERVED_PWA_EXTRA` (space-separated, #133; `k8s.sh` reassigns the template's lists), and define **`project_values <track>`**, whose YAML `deploy` applies last: values for a template the project adds to `helm/cwa/templates`.
- **`k8s.sh` runs under busybox ash on GitLab:** keep the hooks POSIX (no arrays, `declare` or `[[`-only logic in `k8s.sh`). A `DOMAIN` already set when `setup.sh` runs (by `project.sh` or a CI variable) wins over the environment url.
When a project needs something these can't do, add a hook here rather than letting it edit the shared file.

### Deployed images are pinned and promoted (#164)

Builds push only the branch tag (`php:main`, `app:main`). A deploy never runs a moving tag. Before this, pods ran `:main` with `pullPolicy: Always`, so any restart, eviction, scale-up or the 03:00 orphan scan started (and migrated with) a build nobody had deployed. bcio's database was migrated that way by a node rotation.
- **Build:** `--metadata-file` records the pushed digest. `save_image_digest` writes `image_digest.env`: a dotenv artifact on GitLab (`CWA_CI_PHP_IMAGE_DIGEST`, `CWA_CI_APP_IMAGE_DIGEST`), a step output on GitHub.
- **Deploy:** `pin_images <track>` (in `deploy`, before the database guard and helm) resolves the digests and gives helm `<track tag>@<digest>` with `IfNotPresent`; it moves no tag. Review keeps its branch tag, pinned by digest.
- **The track tag moves only after the deploy succeeded (#180).** After helm, `deploy` runs `wait_for_rollouts` (PWA, then API, `CWA_CI_DEPLOY_ROLLOUT_TIMEOUT` each, default 900 s: postStart's warm plus the startup probe's 300 s), then `promote_images <track>` copies the build to `:staging`, `:canary` or `:production` through the registry API (no pull, no new layers; three tries). A failed migrate Job, a pod whose entrypoint migration fails (never ready) or any rollout that doesn't finish fails the deploy and leaves the tag on the last good build, which is still running. A failed copy after a good rollout only warns (failing would skip the purge, #71); the next deploy copies it. Pods pull by digest, so the tag doesn't have to exist first. `deploy` now fails when a rollout fails; it used to return after helm.
- **The track tag is what keeps the registry from garbage-collecting a deployed image** once `:main` moves on. The digest makes it exact, and changes the pod spec so every new build rolls out (a reused image keeps its digest, so it doesn't). The registry holds a fixed set of tags: `main`, `staging`, `canary`, `production`, plus review branches.
- **No digest** (a build skipped with `CWA_CI_BUILD_DISABLED`, or GitHub's `production.yml`, which builds nothing): the deploy pins `:$TAG`'s digest at deploy time. A registry error fails the deploy before helm.
- **Rollback:** re-run the older pipeline's deploy job, which promotes its own digest again. `helm rollback` also works, because each revision records its digest.
- Auth comes from the registry's `WWW-Authenticate` challenge, with `CI_REGISTRY_USER`/`CI_REGISTRY_PASSWORD`. On GitHub the deploy jobs need `packages: write`. `REGISTRY_SCHEME=http` exists only for testing against a local `registry:2`.

### The API is capped at one replica, on purpose

- `autoscaling.maxReplicas: 1` and `CWA_CI_API_AUTOSCALE_MAX` default 1. At 1 the chart renders no API HPA (`cwa.hpaEnabled`, #172), since it couldn't act and showed memory over target for good; the deployment sets `replicas` to `minReplicas`. Raising the max brings the HPA back. Souin's `otter` store is in-memory and purged via `localhost:2019`, so a write on a second pod never purges the first pod's cache (and with a year-long `s-maxage` that is permanent). Mercure's `bolt` transport is pod-local too. One pod served ~974 req/s cached. **More than one API pod only through scaled mode** (below), which moves the cache to Redis and Mercure to its own hub.
- It also resolves the migration race between API pods.
- **Scaled mode (#85; built, and rehearsed on preview.cwa.rocks on 2026-10-20, results in #85):** `CWA_CI_API_SCALED_PRODUCTION`/`_STAGING`/`_CANARY`/`_REVIEW` (off unless `"true"`). Off by default; a site opts in when it needs the redundancy.
  - `check_api_scaling` (in `deploy`, before the cluster) refuses more than one API pod by any route without it (`AUTOSCALE_MIN`/`_MAX` above 1 with the autoscaler, `REPLICA_COUNT` above 1 with `CWA_CI_API_AUTOSCALE=false`; like the chart, it ignores the setting that has no effect, #184), and refuses `CWA_CI_RESET_DATABASE`, a hand-set `CWA_API_CADDY_CACHE_STORAGE` or a bad `CWA_CI_API_REDIS_MEMORY` with it. Defaults in scaled mode: min 2, max 3. `bin/test/api-scaling-config.sh` (unit-tests job) is the case table.
  - **Database connections (#193):** in scaled mode `check_api_scaling` also prints the most connections the API may open: peak pods (the max plus the rollout's `maxSurge` 2, or the min plus `CWA_CI_API_WARM_SURGE`, whichever is higher) × `CWA_CI_API_WORKERS` + 5 for Jobs and console commands. The defaults need 25. Against the in-cluster PostgreSQL's 97 usable (`max_connections` 100, 3 reserved) it warns past that (`::warning` on GitHub); with an external database it prints the number to check, since tracks or apps sharing that database add theirs. It never fails the deploy. On stdout, so the callers that silence `check_api_scaling` don't repeat it.
  - The chart's `scaled.enabled` starts one Redis per release (`templates/redis.yaml`, labels `cwa-redis`, never the API's name label) and points Souin at it through `CADDY_CACHE_STORAGE`, a whole `redis { configuration { … } }` block from the Secret (Caddy expands `{$VAR}` before parsing, newlines included). Timeouts are 100ms with no retries: with Redis down, requests are served uncached (`detail=REDIS-INSERTION-ERROR`) and caching resumes by itself when it's back (measured 2026-10-20). The password comes from `REDIS_PASSWORD`, else the deployed Secret, else is generated (this cluster doesn't enforce NetworkPolicy: legacy datapath). Its memory request and limit are `maxmemory` × 1.4 + 16Mi: **374Mi** for the default 256Mi (`CWA_CI_API_REDIS_MEMORY`).
  - Every scaled deploy runs the full flush and `warm_api_cache`, because Redis outlives the pods.
  - **Post-rollout cache check (#193):** after a scaled deploy's flush, warm and surge end, `api_check_shared_cache` requests `/_api/_/site_config_parameters.jsonld` through the API service from a ready pod, up to 3 times, until a `Cache-Status` is a `hit` with `detail=REDIS`. Otherwise it prints a `!!!! SCALED MODE: THE API CACHE IS NOT SHARED IN REDIS !!!!` banner (`::error` on GitHub) but **returns 0**: the release is already live, and failing would skip the job's later steps (`finish_maintenance_window`, `delete canary`/`staging`, `persist_environment_url`) without fixing anything. Single-pod deploys don't run it. `bin/test/api-warm-surge.sh` covers it.
  - **Turning it off:** set the switch to `"false"` (or delete it) and deploy. Helm removes Redis and the hub and php goes back to one pod with otter and its own hub. Without Cloudflare that deploy runs `purge-rendered-html`, not a full flush: safe, because the single new pod starts with an empty cache. With `provider cloudflare` it flushes as always. An older pipeline's rollback (before scaled mode) also deploys one pod.
  - **Redis and the hub are one copy each:** `safe-to-evict: "false"` but no PDB (one replica would block every drain, as with the single API pod), so a node drain or upgrade still stops them for a while. Redis restarts empty (pages are slower until warm; nothing is stale) and the hub's subscribers reconnect; neither takes the site down (rehearsed: 100/100 requests answered through a Redis restart, an editor's save returned 200 with the hub deleted).
  - **Planned spikes:** raise `CWA_CI_API_AUTOSCALE_MIN` and deploy, then put it back and deploy again; a deploy's own warm uses `CWA_CI_API_WARM_SURGE`. A manual `api scale <track>` job was planned and dropped (#193): a deploy already sets the HPA, and a separate job would leave the minimum out of step with the CI variables.
  - **Mercure gets its own pod** (`templates/mercure-hub.yaml`, labels `cwa-mercure`): the php image's own `frankenphp` with `/etc/caddy/mercure-hub.Caddyfile`, so the Mercure version always matches php's, and no entrypoint (no database, no migrations). The hub settings live once, in `api/frankenphp/mercure-hub.caddy`, imported by php's Caddyfile and the hub's: **edit them there, never inline.** php publishes to `<fullname>-mercure` (`mercure-url`), and `MERCURE_HUB_UPSTREAM` turns php's own hub off (`@local_hub`) and reverse-proxies `/.well-known/mercure` to the hub's pod (`@remote_hub`, `flush_interval -1`), so the ingress and TLS are unchanged. `caddy-validate.sh` provisions both modes and the hub's Caddyfile. Measured locally (2026-10-20): an admin's draft update published through php reached a subscriber connected through php; with the hub stopped, saves still return 200 (the bundle's `MercureResourcePublisher` catches and logs publish failures).
  - **The hub's Caddyfile sets `grace_period 5s`** (global block of `mercure-hub.Caddyfile`, not the shared `.caddy`). Caddy's default grace period is eternal and an open SSE subscription never finishes, so a stopped hub waited for the kubelet's SIGKILL and the pod ended as `Error` (reproduced with `php:main`: `docker stop` with one subscriber, exit 137 after 10 s; with the grace period, exit 0 after 5 s). Subscribers are cut and reconnect. The API pods had the same problem (preStop's `kill -QUIT 1` made Caddy exit 2): their Caddyfile now sets `grace_period 15s` and preStop only sleeps 5 s, so the kubelet's SIGTERM stops Caddy gracefully and it exits 0 (measured with one SSE subscriber: exit 137 at 30 s before, 0 at 15 s after). Keep 5 + 15 s under the pod's 30 s termination grace.
  - Testing Mercure by hand: an edit to a published component publishes a **private** draft update, so an anonymous `match=*` subscriber sees nothing. Subscribe with the admin's `__Secure-mercure_access_token` cookie (over plain HTTP, pass it as a `Cookie` header: curl won't send a `Secure` cookie there).
  - **php pods in scaled mode:** a PDB (`templates/pdb.yaml`, `maxUnavailable: 1`, selecting `cwa.selectorLabels` only: checked against Redis, the hub, SSR, PostgreSQL and the CronJobs), hostname spread, no `safe-to-evict`, no postStart warm, and the HPA on CPU only with `scaleUp` 0 s / `scaleDown` 600 s. Off mode renders byte-identical to before (compare `helm template` output, ignoring PostgreSQL's random password). `deployment.yaml` also `fail`s on more than one API pod without `scaled.enabled`, for a bare `helm install`.
  - **Warm surge:** `CWA_CI_API_WARM_SURGE` extra API pods for a deploy's flush and warm (`api_warm_surge_start`/`_end` patch the HPA's `minReplicas`, wait up to `CWA_CI_API_WARM_SURGE_TIMEOUT`, 300 s, and warm on whatever is ready). In scaled mode every post-flush warm (`warm_api_cache_for`: deploy, fixtures, image variants) goes **through the API service** (`--base-url=http://<fullname>`, the same host key as SSR) at `CWA_CI_API_WARM_CONCURRENCY` (default 2) requests per pod, times the pods during the warm (minimum plus surge, #195), so the pods share the renders; in one pod (`http://localhost`) the surge would sit idle. A job that dies mid-surge leaves the higher minimum until the next deploy resets it. `bin/test/api-warm-surge.sh` (stub kubectl) checks the order.
  - **Scaled browser tests:** `E2E_SCALED=true sh e2e/run.sh` (CI: `CWA_CI_E2E_SCALED="true"`) adds `e2e/compose.scaled.yaml`: two php replicas under the one `php` service (Docker's DNS spreads SSR's and the browser's connections across them), a Redis and the hub, with the chart's store block and `MERCURE_HUB_UPSTREAM`. `compose exec php` reaches the first replica, which is enough for the flush (the cache is shared). Both replicas starting together also exercise the migration lock.
  - **`bin/test/database-guard.sh` and `deploy-promotion.sh` need busybox ash or a modern bash** (CI's shells): macOS's `sh` (bash 3.2) fails them. Run them with `docker run --rm -v "$PWD:/w" -w /w busybox:1.37 sh bin/test/<test>.sh`.
- **Commands in the API run in a ready pod (`api_ready_pod`), never `kubectl exec deploy/…`:** right after a rollout, `deploy/…` can pick the old pod while it terminates. Found on preview's first scaled deploy (2026-10-20): the flush emptied the old single-mode pod's own cache instead of Redis, and the warm then reported every request a hit. The helper picks a Ready pod with no `deletionTimestamp` (falls back to the deployment). The warm through the service spreads unevenly (measured 252 vs 38 requests on two pods): kube-proxy balances connections, and the warm keeps a few alive.
  - **The flush and warm wait for the old API pods to be gone** (`api_wait_old_pods_gone`, up to 120 s), not just for the rollout: the service still routes some connections to terminating pods, and on preview's first surge deploy 8 of the `br` warm's 27 requests failed on them. The surge raises the HPA's `maxReplicas` with its `minReplicas` when needed (Kubernetes refuses min > max; preview's first surge was refused at min 4, max 3) and restores both.
  - **The Redis watch (`app:redis-watch`, `templates/redis-watch-cronjob.yaml`, labels `cwa-redis-watch`)** notices an outage, flushes once Redis is back, and emails `MAILER_EMAIL` (the orphan scan's address; empty sends none). On in scaled mode unless `CWA_CI_API_REDIS_WATCH="false"`; `CWA_CI_API_REDIS_WATCH_SCHEDULE` (`*/2 * * * *`). Through the entrypoint with `SKIP_MIGRATIONS=true` and `cwa.phpEnv`; a release whose migration hasn't run yet exits 0 ("not migrated yet").
    - **Signal:** down when every one of 3 attempts (2 s apart) fails: the job's own connection (address and password parsed from `CADDY_CACHE_STORAGE`, Souin's own block, so no extra env) **or php's view**, one `GET /_api/_/site_config_parameters.jsonld` through the API service whose `Cache-Status` says `-INSERTION-ERROR` (`hit`/`stored` = php reached Redis). php's view is what matters: its 100 ms timeouts can fail while the job's 2 s connection works. If only the job fails while php reaches Redis, the run fails as the job's own fault (password, NetworkPolicy) and isn't an outage. Between-run outages the job never sees are covered by Redis's `run_id`: a restart came back empty (no disk), so it only emails ("Redis restarted"), no flush. A partition shorter than the interval with no restart is still missed.
    - **State is in the database** (`redis_watch_state`, one row, `App\Entity\RedisWatchState`, migration `Version20261020162222`), because it must outlive Redis: down since, reason, emailed, run_id, CDN purge pending, an unsent "Redis is back" email. The outage and recovery emails go once each; a failed send is retried by the next run (the recovery one with its original text, #194).
    - **Flush:** `FLUSHDB ASYNC`, equal to Souin's flush here (v1.7.9's `/flush` is `DeleteMany(".+")` on each storer plus the `SURROGATE_` index, all in this Redis, which nothing else uses). A failed flush keeps the outage open for the next run. Measured locally with `docker pause` on a real Redis under the php image's Souin: an entry cached before the pause was still a `hit` after unpause, the job flushed, the next request was `stored`.
    - **Cloudflare:** a tag purge still reaches Cloudflare while Redis is down (the patch purges the request's tags, not stored ones), but the edge can re-cache a stale copy from Redis after it's back, so with `provider cloudflare` in `CADDY_CACHE_CDN_CONFIG` the job also purges everything in the zone through Cloudflare's API (as the patch's `Flush()`: bearer token without `email`, Global API Key with it; 3 tries on 429/5xx). A failed CDN purge is retried next run without flushing Redis again.
    - The Redis NetworkPolicy admits `cwa-redis-watch` pods beside the API's. Not in the scaled browser tests yet.
- **Eviction protection (#78)**, because one replica makes a single eviction an outage:
  - API pod: `cluster-autoscaler.kubernetes.io/safe-to-evict: "false"`. GKE node upgrades still drain it (a brief, unavoidable outage).
  - SSR pods: `pwa-pdb.yaml` with `maxUnavailable: 1`, plus `topologySpreadConstraints` on hostname (`ScheduleAnyway`).
  - No PDB on a single API pod (scaled mode has one, above; on one pod it would block every node drain until GKE force-evicts after an hour). No `minAvailable: 1` on SSR (same, with one replica).
  - **A PDB whose selector matches nothing protects nothing and raises no error.** The PDB selector must equal the SSR labels (`name=cwa-pwa`) and not match the API (`name=cwa`); recheck when labels change.
  - Open: Spot VM preemptions are involuntary; neither the annotation nor the PDB applies.

### ⚠ php probes and the Souin singleflight wedge (#62, #104)

Souin v1.7.9 coalesces upstream fetches through `singleflight` keyed on the cache key, and a call that never returns used to hold its key for the life of the process: every later request on that key waited out the 10s backend timeout and 504'd. On the probe path (`/_api/_/site_config_parameters.jsonld`) that left the pod `0/1` for good: three hours in production (#62), then 35h on cymru-kitchens on 2026-09-30 (#104, after an OOMKill restart). Probing from inside the pod shows it: the probe's exact key (`Host: <pod IP>:80`) 504s while `Host: localhost` answers in milliseconds. Three layers now stop it:
- **`v1.7.9-singleflight-fix.patch`** (darkweak/souin#850, only its `pkg/middleware/middleware.go` hunks) is applied after the purge patch (see *Patched Souin build*): a request whose context ends `Forget`s the key, so a stall costs one timeout, not the key. It protects visitor keys too. Remove it once a Souin release includes #850.
- **`@use_cache` skips the kubelet on the probe path only** (`User-Agent` starting `kube-probe/`). A cached copy can't say whether php answers. Keep it limited to that cheap path, so a faked UA can't make other requests skip the cache.
- **Liveness is the same `httpGet` as readiness** (`periodSeconds: 10`, `failureThreshold: 6`, `timeoutSeconds: 5`), not `tcpSocket`, which passed as long as Caddy listened. A pod whose php stops answering restarts after about a minute; readiness takes it out of service after 30s. The startup probe holds liveness off during migrations. Trade-off: a database outage now restarts the php pod too.
- **A new pod warms `/_api` before its probes start (#160).** A `postStart` hook (`deployment.yaml`) waits for Caddy, then runs the bundle's `warm-http-cache` twice, each for at most `php.warmHttpCacheMaxTime` seconds (`api_warm_max_time <track>`, #217: `CWA_CI_API_WARM_HTTP_CACHE_MAX_TIME_<TRACK>`; production and canary fall back to `CWA_CI_API_WARM_HTTP_CACHE_MAX_TIME`, then 60; **staging and review default to 0**, no warm, since nobody visits them and staging runs under GitLab's production environment; `0` turns both off), all under `timeout` (2 x maxTime + 270s) and `|| true`; output goes to the container log. Kubernetes starts no probe until `postStart` returns, and with one replica the old pod serves meanwhile. It adds no requests: the console process is what `reservedMemory` already covers. Its keys match production SSR's (plain HTTP to a dotless host, `Accept-Encoding: gzip, deflate` → `gzip`; checked 2026-10-13); **dev SSR differs** (HTTPS, `br, gzip, deflate, zstd` → `br`), so a warm doesn't give dev SSR hits. **The second pass sends `--accept-encoding=br` (#170)**, the key browsers and Cloudflare (which offers br to origins) normalise to: on cymru-kitchens' rollout ~40 hydration requests for the home page's components missed the gzip-only warm and were load-shed. gzip goes first because SSR and the deploy's warm job need it. **The php image needs the `brotli` extension (#175):** the warmer decodes a body to follow a route to its manifest and components, and without `brotli_uncompress` the br pass warmed only the 111 route responses on cymru-kitchens (`tests/Unit/BrotliExtensionTest.php`). Only `/_api/_/site_config_parameters` isn't warmed.
- Keep readiness `timeoutSeconds: 5` whatever else changes (the 1s default can lose a cold worker's first request).
- Readiness `initialDelaySeconds: 5` (Caddy serves at ~+6s; 30s was 24–33s of avoidable downtime per eviction). Startup probe `periodSeconds: 5`, `failureThreshold: 60` (300s boot budget for migrations and `ANALYZE`).
- Open (#104): the API container OOMKills about every 16h on cymru-kitchens (1Gi). Measure whether the `otter` store or the workers grow before choosing a fix.
- The PWA's `/_cwa/healthcheck` probe has no Souin in front, so an unset timeout there can only flap. `/_cwa/healthcheck` doesn't call the API; `/_cwa/readiness` does (503 when php is down).

### Scaling and sizing (#69)

- `hpa.yaml` must target the bare `cwa.fullname` (the old `-api` suffix meant the HPA never worked). An HPA's CPU target is a percentage of the **request**. php requests 100m with deliberately **no CPU limit** (Caddy serves cached responses and should burst); never remove the request (a downstream site without one was starved on a busy node and its probes timed out).
- The PWA has its own `pwa.replicaCount`/`pwa.autoscaling` and `pwa-hpa.yaml`. SSR costs ~150ms CPU per render, so a small CPU limit caps throughput at limit/150ms regardless of pods (the old 150m limit meant ~1 page/second). Now 1000m limit / 100m request, and the PWA HPA targets **175%** CPU, i.e. a new pod at ~175m (about one render a second). **Request and target go together:** keep request × target near 175m (it was 250m × 70% until 2026-10-08; with page caching SSR pods idle at 1-5m, so the 250m reservation was mostly unused). Over 100% is valid. HPA also has `scaleUp.stabilizationWindowSeconds: 0`, `scaleDown` 600s. **No memory target on the SSR HPA** (`CWA_CI_PWA_AUTOSCALE_MEMORY_PERCENT` defaults to `~`): Node rarely returns memory and an HPA only scales down when every metric is under target.
- **Per-track sizing in `bin/devops/k8s.sh`** (`CWA_CI_PWA_*` mirroring `CWA_CI_API_AUTOSCALE_*`, plus `CWA_CI_API_CPU_REQUEST`/`CWA_CI_API_MEMORY_REQUEST`/`CWA_CI_API_MEMORY_LIMIT`): `stable` → min 2 / max 6 SSR; `canary` → the same but min 1 (it runs beside production, #124); others → min 1 / max 2 with smaller requests. **Limits are identical on every track.** An explicit env var always wins.
- **Internal API URL:** the chart's `api-url` default is the in-cluster service with `/_api`, and `k8s.sh` passes `apiUrl: ~` so it applies (SSR used to hairpin through the public load balancer over TLS). `apiUrlBrowser` gets the public URL. Keep this default in the chart (`cwa.fullname` handles `trunc 63` and the release-name edge cases).
- **`Chart.lock`**: after editing `dependencies:` in `Chart.yaml`, run `helm dependency update helm/cwa` and commit only `Chart.lock`. CI's `helm_init` rewrites the lock, so a stale one never shows in CI.
- **Rendering the chart locally** needs a scratch copy with `helm dependency build` (downloads postgresql into the gitignored `helm/cwa/charts/`) and the secret values `deploy` passes with `--set`. `helm lint` with ingress **disabled** is worth running: `NOTES.txt` had bad helper names only reachable there.

### Deploy-time page cache: purge, warm, audit

**⚠ Purge after every deploy (#71).** Cached HTML references the `/_nuxt/*` hashes of the build that rendered it; after a front-end deploy those 404 and the page never hydrates, for up to a year in prod.
- `purge_rendered_html [track]` in `k8s.sh` runs straight after `deploy` in all eight deploy steps (GitLab and GitHub, review/staging/production/canary), before fixtures. It finds deployments by **exact** name label (`cwa` = API, `cwa-pwa` = PWA), waits for `rollout status` on the PWA **then** the API (old PWA pods can otherwise render old HTML into the new API pod's empty cache), then `kubectl exec`s `purge-rendered-html` in the API pod. A missing deployment exits 1.
- **Never revert or cherry-pick the purge calls without a bundle lock that has the command** (they shipped together in `dd04960`), or every deploy fails.
- `kubectl exec deploy/…` reaches one pod; that's complete only while the API has one replica.
- Deploys use `purge-rendered-html`, not the full flush (a pod restart already empties `otter`). **With `provider cloudflare` in `CADDY_CACHE_CDN_CONFIG` (#218)** a single-pod deploy then runs `app:edge-cache:purge-everything` (the Redis watch's `CloudflareEdgeCache`): Cloudflare's edge also holds `/_api` responses the `cwa-html` tag doesn't cover (a release changing API output would otherwise leave them stale for a year), but the new pod's own store only holds this build's responses, so it keeps its postStart warm and there's no second warm. Before #218 it ran `purge-http-cache`, which emptied that warm and warmed again (~5 of cymru-kitchens' 12-minute deploy). If the edge purge fails, it falls back to that full flush and warm. Scaled mode always does the full flush (Redis outlives the pods). The match is a POSIX `case` because GitLab runs `k8s.sh` under busybox ash. Staging shares the variable, so its deploys purge the zone too.
- **A full flush in a deploy is followed by `warm_api_cache` (#175)**: the same two passes as the postStart (gzip, then br, `CWA_CI_API_WARM_HTTP_CACHE_MAX_TIME` each, `0` skips), through `kubectl exec` in the API pod, after `purge_rendered_html`'s Cloudflare flush and after `generate_image_variants`' flush. Without it the flush emptied the new pod's postStart warm: on cymru-kitchens a visitor's first home page 33 s later missed on every component and 52 of them were load-shed. It adds up to 2 x max time to those jobs and only warns on failure.

**Cache warm (#80).** `warm_cache [base_url]` reads the sitemap (follows the redirect to `/sitemap_index.xml` and one level of children), rewrites each `<loc>` origin to `https://$DOMAIN` (or the argument), and requests each page anonymously with `Accept: text/html`, 3 at a time (`CWA_CI_WARM_CACHE_CONCURRENCY`). Any non-200 (including 3xx; redirects aren't followed) exits 1 with a `CACHE WARM FAILED` banner and a GitHub `::error`.
- **It runs after the deploy job, never inside it.** A warm failure must not fail a live deploy (the deploy job's `retry: 1` would redeploy the release). GitLab: inside `image variants and warm <track>` (`image_variants_and_warm` in `k8s.sh`), straight after the variants, with `allow_failure: true` and `environment: action: verify`. **It shares that job on purpose (#160):** a separate warm job waited ~50 s for a runner on every deploy (hbcp, 2026-10-13: 51 s before the variants job, a 30 s Job that generated nothing, 49 s before the warm). Never move the warm before the variants (#153). GitHub: a `continue-on-error` step after the fixtures step.
- **Only production is warmed by default.** `CWA_CI_WARM_CACHE_PRODUCTION` is on unless `"false"`; `CWA_CI_WARM_CACHE_STAGING`/`_REVIEW`/`_CANARY` are off unless `"true"`. These are per-track variables, not GitLab environment-scoped ones, because the staging job uses `environment: production`. Production doesn't wait for any warm job.
- Parsing uses `grep`/`sed` under busybox ash (no `jq`/`xmllint` in CI images; GitLab sources `k8s.sh` before `bash` exists). `CWA_CI_WARM_CACHE_INSECURE=true` is for the local self-signed stack only.
- The sitemap must list only real 200 pages (a leftover `test-static` sitemap with a fake URL was removed for this reason).

**Image variants (#152, #153).** `generate_image_variants [track]` generates every image variant not stored yet in **one-off Kubernetes Jobs**, never in the serving pod: `kubectl create job --from=cronjob/<release>-image-variants` (`templates/image-variants-cronjob.yaml`, a suspended CronJob used only as a template: the php image, `cwa.phpEnv` and site env through the entrypoint, like the orphan scan; `backoffLimit: 0`, 1800 s deadline). Each Job runs `imagine:generate -v --max-memory=<CWA_CI_IMAGE_VARIANTS_MAX_MEMORY, 1G>` with its own memory request = limit (`CWA_CI_IMAGE_VARIANTS_MEMORY`, `1536Mi`); exit 3 (stopped at `--max-memory`, bundle 2.0.0-alpha.16) runs another Job, up to `CWA_CI_IMAGE_VARIANTS_MAX_RUNS` (50). Then `purge-http-cache` via `kubectl exec` in the API pod if any were generated, even after a later failure. Exit 137 = the Job's limit, not the site's; 124 = a Job that never finished (unschedulable or past its deadline).
- **Why:** #153. In the serving pod, its first production run (724 originals up to 30 MP) was OOM-killed after 81 variants and the site 503'd; vips allocates outside `memory_limit`, so neither the php budget nor `memory_limit` bounds it. With the job off, the warm made the serving pod generate every page's variants at once and load shedding 503'd visitors for ~5 min.
- **Before the warm, in the same job** (`image variants and warm <track>`, `allow_failure`, `environment: action: verify`). The job runs when either switch is on; a failed half doesn't skip the other, and either failure fails the job. GitHub: a `continue-on-error` step after fixtures, before the warm.
- **`CWA_CI_IMAGE_VARIANTS_PRODUCTION` is on unless `"false"`; `_STAGING`/`_REVIEW`/`_CANARY` are off unless `"true"`.** Proven on preview (2026-10-12): 8 variants of four 24–29 MP originals in one Job, ~30 s, peak ~649Mi of 1536Mi, no API pod restart, then the purge and the warm.

### Migrations before the rollout: plan, backup, maintenance window (#180)

Functions in `k8s.sh` (section *Migrations before the rollout*), the never-installed `templates/database-job.yaml`, and two commands: `app:database:migrations-plan` and `app:database:backup-upload`.
- **The database Jobs come from `helm template`, not a CronJob.** `database_job` renders `templates/database-job.yaml` alone (`--show-only`) from the **live release's** `helm get values` plus `--set-string php.image.tag=<new tag@digest>`, then `kubectl create`s it. So it works before this chart was ever deployed, uses the release's own Secret and ConfigMap (the track's database), and runs the **new** image without promoting it. An empty `databaseJob.task` renders nothing: the chart is byte-identical with the feature off (`bin/test/database-job-chart.sh`, by hand: CI's php image has no helm). The values file holds the release's secrets; it is deleted straight after the render.
- **`SKIP_MIGRATIONS=true` stops the entrypoint migrating** (and `RESET_DATABASE`), for every Job task. It's in the reserved names, so `CWA_API_SKIP_MIGRATIONS` can't switch the API's migrations off. Plan and backup also set `PGOPTIONS=-c default_transaction_read_only=on`, and the plan command makes its own session read-only and checks it: a migration writing from `up()`/`postUp()` (not `addSql`) can't run there. **That doesn't fail the plan (#183)**, or it would block every guarded deploy: PostgreSQL's `25006` (read-only transaction) makes the plan list the pending migrations without SQL, print `CWA_MIGRATIONS_PLAN_INCOMPLETE=1` and exit 0, and `migrations_plan` warns; the backup, Job and window still run. Any other dry-run error still fails it.
- **Plan:** `doctrine:migrations:up-to-date --list-migrations`, then `migrate --dry-run --write-sql`, then the markers `CWA_DATABASE_SERVER_VERSION=` and `CWA_MIGRATIONS_PENDING=` that `k8s.sh` reads. Doctrine prints "Successfully migrated" for a dry run too; nothing ran. With no migrations table (empty database) it counts every migration and shows no SQL (`ensureInitialized` would have to create the table). The GitLab job `migrations plan production` runs after staging (`environment: action: prepare`, `allow_failure`); `CWA_CI_MIGRATIONS_PLAN_PRODUCTION="false"` removes it. GitHub: `production.yml` action `migrations-plan`. Pressing the manual production deploy after reading it is the approval.
- **`database_guard <track>`** runs inside `deploy`, after `pin_images` and before helm (a stopped deploy never reaches `promote_images`, so the track tag stays put). **Production always plans and, with migrations pending, migrates in a Job before helm** (so a failure stops before the rollout, with the old pods still serving; Daniel, 2026-10-20). `CWA_CI_MIGRATIONS_JOB_DISABLED="true"` turns that off, only for a cluster where the Job can't run. **Other tracks do nothing unless a switch is on:** `CWA_CI_MIGRATIONS_JOB_<TRACK>="true"` (STAGING, CANARY, REVIEW), `CWA_CI_DATABASE_BACKUP_<TRACK>="true"`, or the maintenance window. The plan Job costs ~20-30 s per production deploy; a first deploy (no release yet) finds nothing to plan and the new pod creates the schema. Then it plans, and with nothing pending it stops there. Per-track names, never GitLab environment-scoped ones.
- **Backup:** an init container `postgres:<server major>-alpine` (`CWA_CI_DATABASE_BACKUP_IMAGE` overrides; the major comes from the plan) runs `pg_dump --format=custom` from `DATABASE_URL` (Doctrine's `pgsql://` and query parameters converted for libpq; `sslmode` and the `DATABASE_*_CERT` PEMs honoured) and checks it with `pg_restore --list`; the php container uploads it to `gs://$CWA_CI_DATABASE_BACKUP_BUCKET/<folder>/<track>/<release>/<UTC>Z-<sha>.dump` (track `production` for stable) and keeps `CWA_CI_DATABASE_BACKUP_KEEP` (5); only names in that form are ever deleted. A failed backup stops the deploy. The dump's `emptyDir` has a `sizeLimit` (`CWA_CI_DATABASE_BACKUP_STORAGE`, chart `databaseJob.backup.storage`, default 5Gi, #183): a bigger dump gets the Job evicted (a failed backup) instead of filling the node's ephemeral storage under other pods. The printed in-cluster restore reads the Bitnami pod's `POSTGRES_USER`/`POSTGRES_PASSWORD`/`POSTGRES_DATABASE` (checked for chart 14.3.3 by `bin/test/database-job-chart.sh`; re-check on a postgresql chart bump).
  - **⚠ Never the media bucket.** It's public (anyone could download password hashes and emails), and the orphan scan lists the adapter's root, so "delete all" would delete dumps. `database_backup_location` refuses `GCLOUD_BUCKET`; after each upload the command reads the object **without credentials** and deletes it and fails if that works.
  - **⚠ Never the media key.** The upload uses `DATABASE_BACKUP_GCLOUD_JSON`, from the project's `CWA_CI_DATABASE_BACKUP_GCLOUD_JSON` (the key JSON base64-encoded on one line, so GitLab can mask it; raw JSON also works), and refuses to run without it (it would fall back to the node's credentials). `database_backup_key_b64` checks it's a service account key and refuses one with the media key's `client_email`. It reaches helm in a temporary values file (never a command line), becomes a Secret rendered beside the backup Job (named after it, owned by it once created) and is deleted when the Job finishes. Only the backup Job has it; the API pods never do.
  - **The shared bucket (`bin/devops/backup-bucket.sh`, run by a person, never CI):** `gs://silverback-db-backups` in `silverback-web-apps`, `europe-west2`, uniform access, public access prevention enforced, objects deleted after 90 days (a backstop to keep-N: a site that deploys no migrations for 90 days has no backup left). `init` makes the bucket and the custom role `cwaDatabaseBackup` (`storage.objects.create/get/list/delete`, nothing on the bucket or IAM). `project <slug>` makes the managed folder `<slug>/`, a service account `db-backup-<slug>` (shortened with a hash past 30 characters) granted that role on the folder only, and a new key as one base64 line. `verify <slug> <key file>` writes, lists and deletes with the key and checks it can't list outside its folder and that an anonymous read is refused. `CWA_CI_DATABASE_BACKUP_BUCKET` is set once on the GitLab group; the key per project. The folder is `CWA_CI_DATABASE_BACKUP_FOLDER`, else `CI_PROJECT_PATH_SLUG` (GitHub: `owner/repo` lower-cased, every other character a dash), so `project` must get the same slug. Every `project` run creates another key (10 per account at most): pass `--no-key` to re-grant only. `bin/test/backup-bucket.sh` runs it against a stub gcloud.
  - Managed folders need uniform bucket-level access (not hierarchical namespace). Whether `storage.objects.list` granted only on a managed folder lets a prefixed list through was not confirmed from Google's docs: `verify` checks it on the real bucket.
- **Maintenance window: `CWA_CI_MAINTENANCE_DURING_MIGRATIONS="true"`, for one production pipeline only** (a pipeline or manual-job variable on GitLab, the `maintenance_during_migrations` input on GitHub, where the job sets the name so a repository variable is never exported). Never a project default; it can't be enforced on GitLab. Other tracks ignore it (staging deploys in the same pipeline). With migrations pending: `maintenance status` in the live API pod (fails the deploy if the old image lacks the command, api-components-bundle#549), `maintenance on`, backup (if switched on), migrate Job (always, in a window), helm, `purge_rendered_html`, then `finish_maintenance_window`: full flush, `warm_api_cache_for`, `maintenance off`.
  - **Anything failing after "on" leaves maintenance on.** `maintenance-window.txt` holds the backup path, restore commands and the `maintenance off` command; the job's `after_script` (GitLab) or a `failure()` step (GitHub) prints it. A retry (the production job has `retry: 1`) with nothing pending and maintenance still on resumes the window and ends it.
  - **A window marks itself (#182):** before `maintenance on`, the ConfigMap `<fullname>-maintenance-window` (kubectl-made, not helm's, so upgrades keep it; `started`, `pipeline`); `finish_maintenance_window` deletes it after `off`. **Every production deploy** checks it (one `kubectl get`, after the config checks, whatever its switches) and, if present, warns and ends the window after the rollout, so a re-run without the variable no longer leaves the site in maintenance. Maintenance an admin turned on has no marker and is left alone. If the marker can't be created, the window doesn't start (the deploy fails with maintenance off). The notice's by-hand command lists the API pods (`kubectl get pods -l …`) and has a `<ready pod>` placeholder for the person to fill in (never `deploy/…`, which can be a terminating one), then deletes the marker.
- **⚠ A track on production's database never migrates it.** GitLab's staging (and canary) jobs run under `environment: production`, so with an external database (`CWA_CI_POSTGRES_ENABLED=false`, an unscoped `DATABASE_URL`) staging used to migrate production's database on every push, before anyone read the plan. `database_shared_with_production` compares the track's `DATABASE_URL` with production's live Secret `database-url` (host, port and database only, never printed). When they match, `shared_database_guard` replaces `database_guard`: the release gets `php.skipMigrations: true` (`SKIP_MIGRATIONS=true` through `cwa.phpEnv` on the API, CronJobs and database Jobs; a chart value, never siteEnv), no backup or migrate Job ever runs for it, and it plans against production's release:
  - **nothing pending:** deploys normally, without migrating;
  - **pending, staging:** not deployed, exit 0, `deploy-skipped.txt` makes `purge_rendered_html` a no-op; the old staging keeps running, and the production deploy (which needs staging) still runs with its plan, backup and window;
  - **pending, canary:** fails. A canary runs beside production on its hostname: it can't carry a schema change production hasn't made, so deploy production instead.
  - In-cluster PostgreSQL (one per release, the default), a different host or database, or a production release not deployed yet: not shared, nothing changes. `bin/test/deploy-promotion.sh` covers it.
  - **Review apps aren't covered by this (#197)**: they have their own release name and (usually) namespace, so the plan can't run against production's release from there. `review_database_check` instead **refuses** a review deploy whose external `DATABASE_URL` matches production's Secret, read as `RELEASE_PRODUCTION` (default `production`, GitLab's environment slug) in `KUBE_NAMESPACE_PRODUCTION` (default `<CI_PROJECT_NAME>-production`, `set_namespace`'s default). If it can't read that Secret (another namespace name, no RBAC) it only warns. **Review apps must have their own database.** GitHub's review job always uses the in-cluster PostgreSQL (`CWA_CI_POSTGRES_ENABLED: "true"`), so this is GitLab's case.
- `CWA_CI_DATABASE_JOB_TIMEOUT` (1800 s) is each Job's `activeDeadlineSeconds`. `bin/test/database-guard.sh` (unit-tests job, GitLab and GitHub) runs the order, gates and failure paths against stub `kubectl` and `helm`.
- **Pods still migrate as they start** (`app:database:migrate`, behind the advisory lock): a no-op after the Job, and the path for first deploys, rollbacks and a bare `helm install`. Keep it.

### TLS certificate rotation (#86)

Changing the stable ingress's host list in place makes cert-manager put a self-signed certificate in the live secret while it issues (minutes, or an hour of backoff if a challenge fails): a hard outage with HSTS. Let's Encrypt allows 5 certificates per identical name set per week.
- `ensure_tls_certificate` runs in `deploy` before helm (stable track, `CWA_CI_INGRESS_ENABLED=true`, `CWA_CI_CLUSTER_ISSUER` set). Same `dnsNames` as the live ingress's certificate → keep it (almost every deploy). Different → apply `<CWA_CI_TLS_SECRET_NAME>-stable-api-<8-char sha256>`, wait for `Ready` (`CWA_CI_TLS_CERTIFICATE_TIMEOUT`, default 600s), then helm. Not issued → the deploy fails **before helm**, live ingress untouched.
- `cleanup_tls_certificates` keeps the new and previous rotated certificates (label `cwa.rocks/tls-rotation=true`).
- **The live ingress is read by name** (`cwa_fullname` mirrors the chart's `cwa.fullname`), not by label (a site may carry a redirect ingress with the same labels, which would rotate every deploy) and not by host (at launch `DOMAIN` itself changes).
- No RBAC for `certificates.cert-manager.io` → warns and falls back. First deploy → ingress-shim issues as before.
- Only verified against stub `kubectl`/`helm`. Watch the first real hostname change.
- To retire a preview hostname, remove it from `KUBE_INGRESS_ALIAS_DOMAINS` and deploy.

### Review namespaces (GitLab #4)

**Each review app has its own TLS secret (#221):** `tls_secret_name` gives review `<CWA_CI_TLS_SECRET_NAME>-<release>-api` (cut to 63 characters with a hash: cert-manager puts the name in a label), because several review apps can share a namespace (bcio, hbcp-tatt), and one shared `…-review-api` Certificate was rewritten to each deploy's host in turn, so only the newest app had a valid certificate, and stopping one deleted it for the others (the Certificate is owned by the ingress). `delete review` deletes the app's secret, which cert-manager leaves behind. Other tracks keep `<CWA_CI_TLS_SECRET_NAME>-<track>-api`: renaming production's would reissue its certificate. `bin/test/tls-secret-name.sh` (unit-tests job).

`ensure_namespace` never creates namespaces (CI can't create role bindings). `skip_review_without_namespace` runs first in the GitLab review job and exits **3** (`REVIEW_NO_NAMESPACE_EXIT_CODE`) when the namespace is missing, which `allow_failure: exit_codes: [3]` shows orange. **Keep those two numbers in sync.** Only `NotFound`/`Forbidden` count as missing; any other `kubectl` error fails red. Staging, canary and production keep plain `ensure_namespace`. GitHub's `ci.yml` uses a "Check for a review namespace" step that warns and skips. The jobs after an orange review job still run, since `needs` treats an allowed failure as success (#99), so they start with `skip_unless_review_deployed` (no `environment_url.txt`, no deploy).

**`stop review` never checks out its branch (#165).** Merging with *Delete source branch* removes the ref before GitLab runs the stop action, and a normal checkout then fails in `get_sources` (exit 128), stranding the release, its PVCs and its stored files. So the job has `GIT_STRATEGY: none` and its own `before_script`: a sparse, shallow clone of `bin/devops` from `$CI_DEFAULT_BRANCH` via `$CI_REPOSITORY_URL`, copied to `./bin`. It runs the **default branch's** `k8s.sh` and `project.sh`, not the branch's: keep `delete` working from `CI_ENVIRONMENT_SLUG` alone, with nothing else from the checkout. The review job's `environment_url.txt` artifact still downloads. GitHub's `cleanup.yml` is unaffected (it checks out the PR's merge commit).

## CI

- **A push that changes only Markdown files at the root runs no pipeline** (CHANGELOG.md, CLAUDE.md, README.md): GitLab's `workflow:rules` runs a push only when `changes` matches another path (`changes` has no exclusions, so the globs `*/**/*`, `*[!d]`, `*[!m]d`, `*[!.]md` match every other path; checked with Ruby's `File.fnmatch`, which GitLab uses), GitHub's `ci.yml` has `paths-ignore: '*.md'` (root only). A new branch's first push always runs. Schedules, web and API pipelines are unaffected. A pipeline that failed before a docs-only push is retried by hand.
- **GitLab `workflow:rules` has `merge_request_event → when: never`** and `unit tests` has `only: branches` (#88). MR pipelines always failed (no build, missing image). **Don't switch to MR pipelines casually:** every `only:`/`except:` job would need converting to `rules:`, and review apps and image tags are keyed by branch. GitLab won't mix `rules` with `only`/`except` in one job.
- **`production` and `canary` need `build api`, `build app`, `unit tests` and `functional tests`** (all `optional`), not just `staging`, so a manual deploy can't ship the previous image or skip failing tests when `CWA_CI_STAGING_ENABLED=false` (GitLab #1).
- **GitHub Actions** (`.github/workflows/`): `ci.yml` (push: build, unit and functional tests, review or staging deploy), `production.yml` (manual canary/production), `cleanup.yml` (PR closed), `performance-audit.yml` (manual), `publish-create-cwa.yml` (this repo's npm release) and `publish-php-base.yml` (the php base image, *Published php base*), both excluded from generated projects. Images go to GHCR. They call the same `bin/devops/k8s.sh` functions; `install_dependencies` is replaced by `azure/setup-kubectl`/`setup-helm`.
- **GitHub doesn't export variables to jobs** (#91), so every job that checks out the repo runs `bin/devops/github-export-vars.sh` first: it exports all `vars` (repository, organisation, environment) to `$GITHUB_ENV`, like GitLab, leaving any name the job already sets alone. A new variable `k8s.sh` reads needs no workflow change. **Secrets still need an explicit `env:` mapping** (they aren't in `vars`, and mapping them keeps them masked), except site secrets named `NUXT_*` or `CWA_API_*`, which the deploy jobs export with `github-export-secrets.sh` (see *Site settings*). Never interpolate `${{ }}` values from a branch name or PR into a `run:` script; pass them through `env:`.
- **GitHub settings.** Secrets: `KUBECONFIG`, `KUBE_CONTEXT`, `KUBE_NAMESPACE_PRODUCTION`, `JWT_PASSPHRASE`, `JWT_SECRET_KEY`, `JWT_PUBLIC_KEY`, `MERCURE_JWT_SECRET`, `DATABASE_URL`, `ADMIN_PASSWORD`, optional `GCLOUD_JSON`, `CWA_CI_DATABASE_BACKUP_GCLOUD_JSON`, `APP_SECRET`. Variables: `KUBE_INGRESS_BASE_DOMAIN`, `RELEASE_PRODUCTION`, `ADMIN_USERNAME`, `ADMIN_EMAIL`; optional `CORS_ALLOW_ORIGIN`, `TRUSTED_HOSTS` (see *Deploy defaults*), `CWA_CI_DISABLED` (`"true"` in this repo on GitHub, so mirrored pushes don't run the app pipeline), `CWA_CI_BUILD_DISABLED`, `CWA_CI_TEST_DISABLED`, `CWA_CI_REVIEW_DISABLED`, `CWA_CI_STAGING_ENABLED`, `CWA_CI_FIXTURES_ENABLED`, `CWA_CI_WARM_CACHE_*`, `CWA_CI_PERFORMANCE_AUDIT_*`, `GCLOUD_BUCKET`, `GCLOUD_PUBLIC_URL`, `KUBERNETES_VERSION`, `HELM_VERSION`.
- **php image steps that fetch from Debian or Go's module proxy go through `retry-fetch` (#176, #213)**: the builder stage's `go mod download` steps (300 s) and `xcaddy build` (1000 s) too, after sum.golang.org stream errors and 2-minute `go get`s broke downstream builds on 2026-10-20. Retries alone weren't enough: all three attempts on the template's own build hit `sum.golang.org` HTTP/2 stream resets (`stream error … INTERNAL_ERROR`) on different modules, so the builder stage sets `GODEBUG=http2client=0` (Go over HTTP/1.1; checksum verification unchanged). `proxy.golang.org` doesn't serve the checksum database, and `GOSUMDB=off` would drop verification: don't use either. Long term, #208's prebuilt image removes the Caddy build from project builds. Since #208 only the template's own CI and from-source projects run that build; others pull `cwa-php-base`.
- **Debian fetches (#176)** (`api/frankenphp/retry-fetch.sh`): a hard `timeout`, three attempts; apt uses HTTPS from the start. Plain HTTP to deb.debian.org stalled from GitLab SaaS runners in a way apt's own timeouts never ended (a silent hour in `apt-get install`). A new apt or `install-php-extensions` step needs it too; keep the limits' worst case (3 x each) under the 1 h job limit.
- **Image build cache:** `build_api`/`build_app` export the BuildKit registry cache with `mode=max` (builder stages too, so the app's `pnpm fetch` and base setup are reused when the lockfile is unchanged; min mode re-ran them every build), keyed `<repo>-cache:<ref slug>`, and also read the default branch's cache (`default_branch_cache_from`), so a new branch's first build starts warm. The Nuxt build itself (~60 s) runs on every app change; php's expensive xcaddy build is cached until the `dunglas/frankenphp` base images change (deliberately unpinned); a project pulling `cwa-php-base` caches it as a `FROM` layer until it moves to another release's base.
- **An unchanged image isn't built again.** `image_inputs` hashes the build context's git tree (`git rev-parse HEAD:api` / `HEAD:app`), the build options (the php base argument, the target) and the ISO week; the image carries it as the label `rocks.cwa.ci.inputs`. `reuse_image` reads the label on `:<ref slug>`, else on the default branch's tag (a new branch), with `docker buildx imagetools`; on a match the job skips the build (~15 s instead of 1–10 min), tags a default-branch image for the branch (same digest) and records its digest as a build would. **The same digest means no rollout:** the deploys pin it, and the pod template has no per-deploy `timestamp` annotation any more (it forced a restart on every deploy; the chart's `checksum/config`, `checksum/secret` and `checksum/site-env` annotations already restart pods when their settings change), so a push that doesn't touch an image or its settings doesn't restart its pods. To restart pods on purpose: `kubectl rollout restart deploy/<name>`, or `CWA_CI_BUILD_FORCE="true"` (a new digest). The week puts moving base images (`dunglas/frankenphp:latest` in from-source builds, Node) into a build at least weekly, so the first push of a week rebuilds both. `CWA_CI_BUILD_FORCE="true"` always builds. A failed build pushes nothing, so the next push compares with the last good image and builds. Tested in dind against a local registry (first build, README-only push, new branch, changed context, forced).
- **GitLab's build jobs run `install_build_dependencies`, not `install_dependencies`:** they need only docker, buildx and git (the `docker:27` image has all three; git is installed if missing), never helm or kubectl. A build function that needs another tool must install it there.
- Validate with `glab ci lint` and `actionlint`.

## Fixtures and tests

- **⚠ Fixtures append by default.** Without `--append`, `doctrine:fixtures:load` empties every table. Locally: `docker compose exec php bin/console doctrine:fixtures:load --append`. The pipeline's `load_fixtures` appends (#74). Since bundle 2.0.0-alpha.5 (#335), `--append` with a `CwaFixtureBuilder` scaffold is **idempotent**: it creates only what's missing, keeps everything that exists (a page's content is editors' once it exists), and prints a `created …` / `kept …; skipped …` summary. A second append on the template's scaffold exits 0 with identical rows and IDs. So a new page added to a scaffold reaches a seeded site without purging.
- **`CWA_CI_FIXTURES_PURGE` opts a fixture job into emptying the database first** (MR !11; only `load_fixtures` reads it, never a deploy or pod start, unlike `CWA_CI_RESET_DATABASE`):
  - **review:** `"true"` (or `"force"`).
  - **production:** only `"force"`. A project-wide `"true"` meant for review apps prints a notice and appends.
  - **⚠ Staging has no fixture job at all**, on GitLab or GitHub (Daniel, 2026-09-25). Staging's GitLab jobs run under `environment: production` and get production's `DATABASE_URL`, so (whenever production has a `DATABASE_URL`) a staging load would write to production. Don't add one back.
- **Every fixture load ends by flushing the whole HTTP cache** (`silverback:api-components:purge-http-cache`). The load changes the database underneath whatever Souin cached since the deploy, and a purge load deletes rows with plain SQL, so nothing else purges the old content (served for up to a year in prod). A failed load stops before the flush. After the flush, `warm_api_cache` warms `/_api` again (#174), as after a deploy's full flush.
- **Fixtures in CI:** GitLab's fixture jobs (review, production) are manual and gated by `CWA_CI_FIXTURES_ENABLED`. GitHub's "Load fixtures" step runs after each review or production deploy while `vars.CWA_CI_FIXTURES_ENABLED == 'true'` (no manual steps in a push workflow), so set it only for a new environment's first deploy. With `CWA_CI_FIXTURES_PURGE` also set, **every** such deploy purges.
- **The demo site reloads its scaffold daily (#181), and only this repo has the job.** `demo reload production` lives in `.gitlab/ci/template-only.yml`, which `.gitlab-ci.yml` includes only when it exists (`include: rules: exists`); `create-cwa` leaves it out (`alwaysExclude`), and downstream sites must not copy it. Without the file the pipeline is unchanged (checked with the CI lint API: same jobs as before; a bare `include: local` of a missing file is an error, so keep the `exists` rule). The job runs only in a schedule pipeline on the default branch with `CWA_CI_DEMO_RELOAD="true"`: the production fixture job's script (`!reference`) with `CWA_CI_FIXTURES_PURGE=force` exported in the script (a project variable would beat a job variable), so it empties every table, loads, flushes and warms `/_api`; then `warm_cache`. `needs: []` and `action: verify`, so it needs no production job and records no deployment.

## PWA

The module ships no service worker; the template carries the reference config in `app/nuxt.config.ts` (`@vite-pwa/nuxt` in **devDependencies**). Nuxt 4 support is real though undeclared upstream.

- **⚠ `workbox.navigateFallback: null` must be written explicitly.** In the prod build `@vite-pwa/nuxt` defaults it to the base URL when the key is **absent**, serving the `/` app shell for every SSR navigation. Presence of the key, not its value, disables it in prod. In dev, `??` coalesces `null` to `/` anyway, which is one reason `devOptions.enabled` is `false` (enable it only to test the PWA). If an app ever sets a fallback, add `navigateFallbackDenylist: [/^\/_cwa\//, /^\/login/]`.
- **API runtime caching (`cwa-api`, NetworkFirst, 3s timeout)** is safe only because the bundle marks authenticated responses `Cache-Control: private, no-store` (bundle #200) and a `cacheWillUpdate` plugin drops anything `no-store`/`private` or non-200. Draft and published share URLs, so excluding by URL is impossible. NetworkFirst means the cache is read only offline.
- **⚠ The `urlPattern` must be exhaustive and anchored.** It lists `routes`, `resource_manifest`, `pages`, `layouts`, `component_groups`, `component_positions`, `page_data`, `component`. Missing `resource_manifest` silently breaks offline rendering; a broad `/_api` pattern swallows the Mercure stream and `/_api/me`. Test: must match `/_api/_/routes//x`, `/_api/_/resource_manifest//x`, `/_api/page_data/x`, `/_api/component/images/x`; must not match `/_api/.well-known/mercure` or `/_api/me`. Add new module resource types here.
- The API must keep `max-age: 0` with a long `s-maxage`: a browser-cached copy would pass through Workbox's `fetch()` and NetworkFirst would serve it stale. The API deliberately sends no `Vary: Cookie`.
- **`/sw.js` (and the manifest) go out `public, max-age=0, must-revalidate`** via `@vite-pwa/nuxt`'s `registerWebManifestInRouteRules: true` (off by default upstream; alpha.13 used our own `routeRules` with `no-cache` instead). Nitro sent it with no header, and Cloudflare caches `.js` by default, so the edge served the previous build's worker for ~2h after a deploy. Keep it: with it, CDN zones can use Cloudflare's default caching (no blanket bypass rule, no `/_nuxt` exception).
- **Updates: `registerType: 'prompt'`, applied silently on the next path change** by `app/app/plugins/pwa-update.client.ts`, held while `$cwa.admin.isEditing` (an auto-update could swap assets mid-edit). No notice UI (Daniel, 2026-09-21).
  - It uses `afterEach`, not `beforeEach` + `location.assign`: in prompt mode `updateServiceWorker()` ignores its argument, posts `SKIP_WAITING`, and workbox-window reloads on `controlling`, which would race the navigation.
  - **⚠ `clientsClaim: true` is required**, or an uncontrolled page (the first load, or a Shift-reload) is never claimed and the reload never fires. Safe with `prompt` (activation still waits for `SKIP_WAITING`).
  - API traps: the composable is `usePWA()`; `$pwa` is client-only and undefined until registration; `needRefresh` and `$cwa.admin.isEditing` are plain values, not refs; inside `defineNuxtPlugin`, `nuxtApp.$pwa`/`$cwa` are `unknown` (cast via `ReturnType<typeof usePWA>`/`useCwa`) and should be read lazily in the router callback.
- **Session-end cache purge is the module's** (cwa-nuxt-module#293): `cwa.auth.clearCachesOnSessionEnd` defaults to `['cwa-api']`. **If you rename the cache, set the option to match**; otherwise leave it unset. It fires only when a session actually ended (not on an anonymous `/me` 401) and on any 401 while signed in.
- **Mercure reconnect** (module #286) re-fetches on-screen resources but only **stages** changes: admins see "The content on this page is outdated"; anonymous visitors keep stale content until they navigate. Don't describe it as "the page updates itself". Whether that's intended is unconfirmed module-side.
- If a `pwa` choice is added to `create-cwa`, gate the `pwa: {}` block with `// @cwa-if:pwa` like the other features.

## Media and uploads

- **`MEDIA_STORAGE` picks the media adapter at runtime (#211):** `local` stores under `public/uploads` (plus the path prefix) and serves it at `https://<BROWSER_SERVER_NAME>/uploads/`; `gcloud` uses Cloud Storage. Default `gcloud` in prod (every Kubernetes deploy, unchanged), `local` in dev and tests; `compose.prod.yaml` sets `local` with a `media_data` volume. Either way it's the bundle's `gcloud` adapter alias (`MediaAdapterFactory`, Cloud Storage built only when chosen), and `app.media_public_url` comes from `%env(media_url:MEDIA_STORAGE)%` (`MediaUrlEnvVarProcessor`). Another value fails at boot. The orphan scan and `delete-stored-files` work the same on both (the scan skips the imagine `cache/` prefix).

  - `/uploads` bypasses Souin (never in `@use_cache`), so files stream from disk. Variants get no long `Cache-Control` (a variant regenerated under the same name would stay stale).
- **`GCLOUD_PUBLIC_URL`** (#68) sets `app.media_public_url` for the GCS adapter's `public_url` and `FlysystemCacheResolver`. Unset or empty falls back to `https://storage.googleapis.com/<GCLOUD_BUCKET>/` (`MediaUrlEnvVarProcessor`), resolved at runtime, not compile time. Wired: `api/.env` → `php.gcloud.publicUrl` → configmap `gcloud-public-url` → env, and `k8s.sh`. This template's deploy sets `https://cdn.cwa.rocks/` as a GitLab variable.
- **`GCLOUD_PATH_PREFIX` (#166)** puts an app's objects in one path of the bucket (unset: the bucket root, as before). `%env(storage_prefix:…)%` (`PathPrefixEnvVarProcessor`) normalises it to `a/b/`; it goes to the adapter's constructor (the tag config's `prefix` is never read) **and is appended to `app.media_public_url`**, because Flysystem's `public_url` generator and `FlysystemCacheResolver` both build URLs from the unprefixed path. The orphaned-file scan lists the adapter's root, so it stays inside the prefix: **apps sharing a bucket need a prefix each**, or each one's scan sees the others' files as orphans and "delete all" removes them.
  - **Review apps always get `<GCLOUD_PATH_PREFIX>review/<slug>/`** (`gcloud_path_prefix` in `k8s.sh`; `<slug>` is `CI_ENVIRONMENT_SLUG` without its leading `review-`, #173, so alpha.37's `review/review-<slug>/` review apps move path on their next deploy, as in #169), so a project-wide prefix can't put them in production's path. `delete review` runs the bundle's `delete-stored-files gcloud --all` in the API pod before `helm uninstall` (api-components-bundle#477), guarded by `--only-if-value="$GCLOUD_PATH_PREFIX" --matching='~(^|/)review/[^/]+/$~'`, read in the pod: a review app deployed before #166 has no prefix, and `--all` there would empty the bucket. **Never drop the guard.** A failure only warns, naming the app's real path; a bucket lifecycle rule is the backstop.
  - **The deploy tidies the prefix exactly as php does (#168):** `gcloud_path_prefix` trims whitespace, drops empty segments and refuses `.`/`..` with php's message, before any `kubectl` or `helm` call, and the pod gets the tidied value (`site-a//` → `site-a/`, review `site-a/review/<slug>/`). `bin/test/storage-prefix-parity.sh` (unit-tests job, GitLab and GitHub) runs one case list through both and fails on any difference; add a case there and in `StoragePathPrefixTest` together. It sources `k8s.sh` with busybox ash if present (GitLab's deploy shell), else bash (the php image's `sh` is dash, which can't). Alpha.37 pods with `site-a//review/<slug>/` still match the stop guard's regex.
  - **The deploy also refuses a `review` segment in `GCLOUD_PATH_PREFIX`** (k8s.sh policy, not php's): `review/` is where review apps store, so its lifecycle rule would delete the project's own uploads. e2e sets `review/e2e/` directly in `e2e/compose.yaml`, not through `gcloud_path_prefix`.
  - **The lifecycle rule (#169):** one per prefixed app, `matchesPrefix: ["<GCLOUD_PATH_PREFIX>review/"]` (`["review/"]` with no prefix). `age` counts from each object's creation, not the app's, so a review app that lives longer than it loses its older uploads: choose an age longer than review apps live; it's only a backstop.
  - **Review apps deployed before alpha.37 (#169)** stored at the bucket root with root-relative database paths. Their next deploy uses `review/<slug>/`, so earlier uploads 404 and drop out of the orphan scan, and the stop guard (correctly) won't delete root objects. No code workaround: redeploy them with fresh fixtures (`CWA_CI_FIXTURES_PURGE=true` on the review fixture job), or stop and recreate them, then remove their old root objects by hand.
  - **Changing an existing app's prefix moves every media URL**: database paths are relative to the adapter, so move the objects under the new prefix first.
  - The browser tests run with `review/e2e/`: `run.sh` fails on any object outside it or left after the guarded delete.
  - It applies to `local` too (`public/uploads/<prefix>`).
- Dev uses `local` (originals and variants at `https://localhost/uploads/`); a dev stack's files are in `api/public/uploads` (gitignored).
- **Upload sizing:** `upload_max_filesize = 20M`, `post_max_size = 21M` (`10-app.ini`), `Assert\File(maxSize: '20M')` on `Image::$file`. The ingress allows 30m.
- **Two `memory_limit`s (#136).** Requests run under `FRANKENPHP_MEMORY_LIMIT` (`php_ini` in the Caddyfile's `frankenphp` block, default `128M`); console commands under `10-app.ini`'s `256M` (fixture load ~60 MB, `cache:clear` ~100 MB, the PHPUnit suite ~110 MB). A worker request with opcache measured ~14 MB. **In worker mode an `ini_set('memory_limit')` outlives the request**, so anything that raises it must restore it.
- **Imagine filters (bundle ≥ 2.0.0-alpha.11, api-components-bundle#397):** generation raises `memory_limit` to `silverback_api_components.imagine.memory_limit` (the bundle's default `320M` since 2.0.0-alpha.12; the template doesn't set it, and the chart's `php.imagineMemoryLimit` mirrors it) and restores it; a filter whose estimate (GD 12 MB per megapixel, plus the worker's usage) won't fit is skipped and logged, and the original is served. `Image::$file` rejects over **30 MP** with a 422 (`Assert\Image(maxPixels: 30_000_000)` inside `Assert\When`, so SVG is exempt): what 320M can thumbnail with vips (the bundle estimates 8 MB/MP; GD's 12 MB/MP stops at ~23 MP, so switching back to GD means lowering this to 20 MP). The module downscales above 20 MP anyway (module #335), so the limit is for direct API uploads.
- **The imagine driver is libvips (#141)**, through php-vips 2 (FFI) and `rokka/imagine-vips`; `driver: gd` in `liip_imagine.yaml` switches back (GD stays installed). Measured (#141): a 12 MP JPEG thumbnail ~200 ms and ~50 MB RSS vs GD's ~320 ms and 140 MB; a 48 MP one ~10 MB of PHP memory vs GD's 560 MB (fatal at 320M). vips memory is native, outside `memory_limit`.
  - **⚠ `vips_init` isn't thread-safe:** concurrent first use in FrankenPHP worker mode segfaults (`cannot retrieve class for invalid (unclassed) type`). `config/preload_vips.php` runs it before the threads start: required by `config/preload.php` (prod) and preloaded directly in dev (`20-app.dev.ini`). Don't drop it while the driver is vips.
  - `ffi.enable = true` (`10-app.ini`): php-vips can't use `preload` mode. The PECL `vips` extension (php-vips 1.x) avoids FFI but is deprecated upstream (last release 2022).
  - Image `ENV`s, overridable as `CWA_API_*`: `VIPS_BLOCK_UNTRUSTED=1` (no ImageMagick, PDF or SVG loaders; the bundle skips SVG anyway), `VIPS_CONCURRENCY=2` (the default is one thread per node CPU, and memory grows with it), `MALLOC_ARENA_MAX=2` and `MALLOC_MMAP_THRESHOLD_=1048576` (without them php kept 200-300 MB more RSS after concurrent generations).
  - Decoded images over 100 MB (~33 MP RGB) go to a temp file in `/tmp`, not memory (`VIPS_DISC_THRESHOLD`). Debian's `libvips42t64` adds ~100 MB to the image (~32 MB compressed) and is named for trixie: a new base Debian may rename it.
  - Both drivers drop the ICC profile (Imagine's `thumbnail()` strips), so Display P3 photos lose saturation; vips slightly more (it converts P3 as if sRGB). vips JPEGs are progressive and not chroma-subsampled at `jpeg_quality` 90 or more (~25% bigger than GD's); only relevant if a filter set drops `format: webp`.
- **Filters and encoding (#143):** `thumbnail` (500 px inset) for listings and admin, `general` (1200 px inset: the layout's widest content column is 1216 px) for display, `large` (2400 px inset, `general` at 2x); the `Image` component renders `general` as `src`, with the module's `srcset` (every variant with a width, the original included) and `sizes` of `general`'s width, and the module falls back to the original when it's missing (SVG, or skipped over the budget). **Every variant is WebP (#149)**, whatever the upload's format: `format: webp` on all three sets, so a PNG logo or screenshot isn't served as PNG at every size (smokinginwales' 128 KB `general` PNG logo is 41.5 KB as WebP, its thumbnail 40 → 15 KB; no visible difference at 2x). WebP keeps transparency. vips always saves WebP at quality 80 (`webp_quality`, which liip never forwards); `quality: 80` sets GD's to match (liip's default is 100). `tests/Functional/ImagineFilterTest.php` runs the real filter sets on a transparent PNG and a JPEG and fails if a variant isn't WebP. **A filter is generated on the first read of the resource that lacks it** (`MediaObjectFactory` → liip's `getUrlOfFilteredImage`), within the budget; deleting a filter's stored files (`cache/<filter>/`) regenerates them the same way. Changing a filter's options doesn't touch stored files.
  - `requiredOnPublish: true` on `Image::$file`: publishing without a file is a 422 (`tests/Functional/ImageTest.php`). Fixtures skip validation, so the scaffold's file-less draft image still loads.
  - Since bundle 2.0.0-alpha.13 (#404) a variant is stored with its format's extension, so WebP is served as `image/webp`. Changing a filter's `format` regenerates its variants under new names; the old files stay until `bin/console liip:imagine:cache:remove --filter=<filter>`. **`srcset` (module 2.0.0-alpha.10, #377)** always includes the original upload, so without `large` a retina desktop (a ~1200 px slot needs ~2400 px) downloaded the original, often several MB. Keep a filter at about twice the widest display size. `Image.vue` is a plain `<img>`: `NuxtImg` reads `sizes` as its own spec and builds its own `srcset`.
- **FrankenPHP worker pool is fixed** at `FRANKENPHP_WORKER_NUM` (`worker.Caddyfile`, default 4; the default follows node CPUs, and with it worst-case memory).
- **php pod memory budget (#136):** `workers × memoryLimit + (imagineMemoryLimit − memoryLimit) + reservedMemory + Go ≤` the limit; defaults 4 × 128 + 192 + 160 leaves Go **160Mi** of 1Gi. `reservedMemory` covers opcache (~45 MB measured on the API paths), APCu, the binaries and an exec'd console command. Chart values `php.workers`, `memoryLimit`, `imagineMemoryLimit`, `reservedMemory` (`CWA_CI_API_WORKERS`, `CWA_CI_API_PHP_MEMORY_LIMIT`, `CWA_CI_API_IMAGINE_MEMORY_LIMIT`, `CWA_CI_API_RESERVED_MEMORY`; Mi/Gi); the chart sets `FRANKENPHP_WORKER_NUM` and `FRANKENPHP_MEMORY_LIMIT` from them (reserved names). `imagineMemoryLimit` only describes the bundle config: change both together. `check_php_memory_budget` (in `deploy`, before the cluster) fails when Go would get under 64Mi.
  - **`GOMEMLIMIT`** is what the budget leaves Go, at least 64MiB (`cwa.php.goMemLimit`, Mi/Gi limits only; `CWA_CI_API_GOMEMLIMIT`/`php.goMemLimit` overrides, `off` unsets). It bounds only Go's heap (Caddy, Souin, Mercure), and only softly: the `otter` store isn't capped by bytes, so a big cache makes Go collect harder rather than stop. Deployment only, not in `cwa.phpEnv`.
  - The budget assumes **one** filter generation at a time; two at once (e.g. two workers on the same new image) can pass it by 192Mi, normally absorbed because workers sit far below their limit.
  - Limit 1Gi (`CWA_CI_API_MEMORY_LIMIT`), request 350Mi; the request stays low on purpose, at the cost that a node short of memory evicts this pod first. If a cluster forces limits to equal requests (GKE Autopilot), lower `CWA_CI_API_MEMORY_LIMIT` and the budget with it.

## CORS: `Retry-After` is exposed (#100)

Throttled email requests (api-components-bundle#331) return 429 with `Retry-After`, and the module's resend link counts down from it (cwa-nuxt-module#353). Browsers only let cross-origin JavaScript read CORS-safelisted headers plus those in `Access-Control-Expose-Headers`, so `nelmio_cors.yaml` exposes `Retry-After` alongside `Link`. The template's own browser calls are same-origin `/_api`, so this only matters for a site that serves the API from another origin. Don't drop it from `expose_headers`.

`allow_headers` also has `X-CWA-Client-Id` (#219): the module's co-editing (cwa-nuxt-module#429) sends it on every write, and a cross-origin preflight without it fails. It went in before the module sends it (alpha.46); allowing a header early is harmless. Likewise `If-Match` (allowed) and `ETag` (exposed), bundle alpha.36's write check (#219).

## Production logging and the error mail (#162)

Ported from bcio (`api/config/packages/prod/monolog.yaml`, `App\Monolog\ErrorMailHandler`, `tests/Unit/Monolog/`).
- **prod logs to stderr as JSON, not a file.** A file inside the container is lost on every restart, and the cluster's logging agent ships stderr (GKE: Cloud Logging). It's Google's structured shape, so severity, channel and context are queryable. There's no `var/log/prod.log` any more: read `kubectl logs`, or the cluster's log explorer. `fingers_crossed` still writes only on an error, so a quiet request logs nothing.
- **Redaction is a formatter** (Monolog's `RedactingFormatter`, around `GoogleCloudLoggingFormatter`), so it also reaches secrets copied into exception messages. It masks emails, JWTs, DSN credentials, bcrypt hashes and the username and token segments of the email-link paths. `ProdLogRedactionTest` reads the keys and patterns from the YAML, so loosening it fails. **A new field or URL that carries a secret or an email address needs a key or pattern there, and a test.**
- **Error mail:**
  - One email per unique 5xx per hour to `ERROR_MAIL_TO` (deploys: `CWA_API_ERROR_MAIL_TO`, through the passthrough; empty sends none and never fails boot).
  - It triggers at `critical`, which is what Symfony logs 5xx at (4xx is `error`).
  - It's one email per request, deduplicated per pod and reset by a restart. The `mailer` channel is excluded, and a failed send is swallowed.
  - The subject is `WEBSITE_NAME` + " API error" and must never carry the record (the parent formats it unredacted).
- **The browser tests fail the run on any error mail** (`e2e/run.sh`, `ERROR_MAIL_TO: errors@cwa.test`), so a 5xx the UI hides still fails CI.
- **Proven in the prod image** (2026-10-14, e2e stack with the database stopped): two 500s sent one mail, and neither the mail nor the stderr JSON contained the email address or token from the URL.

## Security and secrets

- **`JWT_COOKIE_SAMESITE` defaults to `strict` (alpha.46):** the login cookie (`api_component`), the Mercure cookie and the Symfony session cookie are never sent on a request another site starts. An admin following a link from another site gets the anonymous (cached) page, then the module's client-side `/me` signs them back in; `e2e/tests/admin.spec.ts` checks it. A site whose API is on another registrable domain than its front end needs `none` (`CWA_API_JWT_COOKIE_SAMESITE`); `lax` restores the old behaviour.
- **Deploy secrets keep their values (#144).** `deploy_secrets` (in `deploy`, after the kube context) takes `APP_SECRET`, `NUXT_APP_SECRET`, `MERCURE_JWT_SECRET` and the JWT key pair from a CI variable, else from the release's live Secret, else generates them, so a rollout's old and new pods agree and logins, signed URLs and Mercure cookies survive a deploy. Jobs no longer call `generate_jwt_keys` themselves: a call before `deploy` would generate before the live values are read. The chart's own random `php.appSecret` default is only for a bare `helm install`.
- **`NUXT_APP_SECRET` signs OG image URLs** (nuxt-og-image 7, module alpha.16). Without it, every `/_og/` image is a 500 and pages still render. Every SSR pod must share it, because one pod renders the URL and another may serve the image. `deploy_secrets` reads the live value from the `<release>-pwa-env` Secret and passes it through the `NUXT_*` passthrough, so `deploy` runs `site_env_values` again after it. The deploy fails if the value is under 32 characters.
- **`ensure_jwt_keys` (`k8s.sh`, from `deploy_secrets`):** with no `JWT_SECRET_KEY` it generates a key pair (and a passphrase if none is set). With a key but no `JWT_PUBLIC_KEY`, it derives the public key and fails the deploy if the passphrase doesn't decrypt the key. **A key without a passphrase fails the deploy**, rather than getting a random passphrase that could never match. Use quoted POSIX `[ ]` tests on PEM values: busybox ash splits an unquoted multi-line key inside `[[ ]]` and the test silently becomes false.
- **⚠ Anchor every `TRUSTED_HOSTS` alternative: `^(?:a|b|c)$`.** Symfony wraps the pattern as `{…}i` without anchoring it, so in `^a|b|c$` only `a` is anchored at the start and `c` at the end, and `b` matches anywhere (`evil-caddy.attacker.net` passed the old `api/.env` default). Fixed in `api/.env`, `k8s.sh`'s functional-test default, `compose.yaml` and `helm/cwa/values.yaml`. Project CI variables must follow the same form.
- **Single-server production (`compose.prod.yaml`) is a PREVIEW for the beta (#207):** media is local (#211) and `bin/server/` deploys and backs it up (#212), but it hasn't run a production site yet. It mirrors what `apply_site_defaults` and the chart set for one host, and CI boots it (the browser tests, above).
- **`bin/server/` runs a single-server site (#212)**, POSIX sh (a server's `/bin/sh` is often dash), from the checkout on the server:
  - **`init`** writes `.env.prod` (mode 600, never overwritten; `CWA_SERVER_ENV_FILE` names another): random secrets, a 4096-bit JWT pair (derived as `e2e/run.sh` does), `COMPOSE_FILE=compose.yaml:compose.prod.yaml`, and `SITE_HOST`, `SITE_ALIASES`, `MAILER_DSN` from the environment or asked. The PEMs are double-quoted multi-line values, which compose reads whole (checked), so `compose.prod.yaml`'s env contract is unchanged. Every script reaches compose through `c` in `lib.sh` (`docker compose --env-file .env.prod`).
  - **`deploy.sh [--fixtures]`**: build (`--pull`), database up, then (when a php container already exists) the new image's `app:database:migrations-plan` read-only in a one-off container and `backup.sh` if anything is pending, `up --wait` app then php then the rest, `--fixtures` (append), `purge-rendered-html`, the `/_api` warms (`warm_api`, as a pod's postStart; `CWA_SERVER_WARM_HTTP_CACHE_MAX_TIME`), image variants, the page warm. **Image variants run in one-off `compose run -d` containers capped by `docker update --memory`** (`CWA_SERVER_IMAGE_VARIANTS_MEMORY`, 1536m, applied while the kernel boots; `compose run` has no memory flag), never the serving php (#153); exit 3 runs another. **The page warm** is `bin/lib/site.sh`'s `warm_cache` with `--resolve SITE_HOST:443:127.0.0.1`, and only warns. No Cloudflare purge: compose passes no `CADDY_CACHE_CDN_CONFIG`.
  - **`backup.sh`** writes `backups/<UTC>-database.dump` (`pg_dump -Fc` in the database container, checked with `pg_restore --list` before it's kept), `-media.tar.gz` and `-caddy-data.tar.gz` (the TLS certificates), keeping `CWA_SERVER_BACKUP_KEEP` (5); only names in that form are deleted. **`restore.sh [<time>] [--certificates] [--yes]`** asks for the host, turns maintenance on, restores the database (`--clean --single-transaction`), **turns maintenance on again (it's a site setting, so the dump brought the backup's back)**, replaces the media, restarts php (it migrates a restored older schema), purges, maintenance off. `cron.example` has the daily backup and orphan scan.
  - **`bin/lib/site.sh`** holds `sitemap_pages` and `warm_cache`, moved from `k8s.sh`, which sources it (`CWA_SITE_LIB` from outside the repository root; `bin/test/database-guard.sh` sets it). It stays in `ci: none` projects. `stop review`'s sparse clone includes it. `CWA_CI_WARM_CACHE_CURL_OPTS` adds curl options to the warm. `bin/test/site-lib.sh` (unit-tests job) runs the warm under plain sh against `php -n -S` and checks `k8s.sh` still provides it.
  - **`bin/test/server-scripts.sh`** (template CI's `server scripts` job, `.gitlab/ci/template-only.yml`; on its paths, else manual) runs init, `deploy.sh --fixtures`, an admin login, `backup.sh`, an upload (`e2e/media-checks.sh`), `restore.sh --yes` (the upload is gone, maintenance off) and a second deploy (nothing pending) against this ref's images, with `e2e/compose.yaml` added to `COMPOSE_FILE`, under `env -i`. The page warm can't reach the stack there (no published ports) and warns.
- **`compose.prod.yaml` gives `app` its URLs (#98):** SSR uses `NUXT_CWA_API_URL=http://php.local/_api`, the warm uses `NUXT_CWA_PAGE_CACHE_WARM_ORIGIN=https://php.local`, the browser uses `https://$SITE_HOST/_api`, and php gets the `php.local` network alias plus `BROWSER_SERVER_NAME=$SITE_HOST`. **Not `http://php`:** only `php.local:80` is in Caddy's `SERVER_NAME`, so anything else over plain HTTP is 308'd, and so is `php.local` with the public `Host`, which is why the warm must be HTTPS.
- **Its inputs are `SITE_HOST` (one host) and `SITE_ALIASES` (optional, space-separated; Caddy refuses `a,b` in `SERVER_NAME`)**, compose-level names, so not `CWA_CI_`. `SERVER_NAME` is `$SITE_HOST $SITE_ALIASES, php.local:80, php.local:443`; `NUXT_SITE_URL`, `MERCURE_PUBLIC_URL` and the browser API URL use `SITE_HOST`; `CWA_ENVIRONMENT`/`NUXT_PUBLIC_CWA_ENVIRONMENT` default to `production`. `SERVER_NAME` as an input is gone (compose.yaml's dev default still reads it).
  - **Compose can't escape or anchor**, so `TRUSTED_HOSTS`, `CORS_ALLOW_ORIGIN` and `MERCURE_CORS_ORIGIN` are passed empty and the php entrypoint fills them (`api/frankenphp/site-hosts.sh`, sourced from the entrypoint's own directory so dev's bind-mounted entrypoint finds it too) exactly as `apply_site_defaults` does: `^(?:a\.com|b\.com|localhost)$`, `^https://(?:a\.com|b\.com)$`, `https://a.com https://b.com`. A non-empty value wins; no `SITE_HOST` (dev, Kubernetes, which sets all three) changes nothing; a host with a scheme, port or other character stops the entrypoint. `bin/test/site-hosts-parity.sh` (unit-tests job, GitLab and GitHub) compares the two. **`docker compose exec php bin/console` skips the entrypoint**, so it sees them empty: harmless for the console, never for HTTP.
  - Also: `MAILER_DSN` required (otherwise `api/.env`'s `smtp-relay:25`), `MEDIA_STORAGE` (default `local`, in the `media_data` volume), `MAILER_EMAIL`, `ERROR_MAIL_TO`, `GCLOUD_BUCKET`/`_JSON`/`_PUBLIC_URL`/`_PATH_PREFIX` passed through (for `MEDIA_STORAGE=gcloud`), json-file log rotation (10m x 5) on php, app and database, `restart: unless-stopped` on all three, and php waits for a healthy database. The image healthchecks (#205) make `up -d --wait` meaningful.
  - `bin/test/compose-prod-config.sh` (the light `compose config` job, GitLab and GitHub: the compose CLI only, no daemon) renders it with dummy values, checks those settings and that 2019 isn't published, fails if it renders without any required value, and renders the dev stack with nothing set. It runs `docker compose` under `env -i` with `--env-file /dev/null`, so a local `.env` can't satisfy a requirement.
- **`compose.prod.yaml` requires every secret and site value** with `${VAR:?…}`: `SITE_HOST`, `APP_SECRET`, `NUXT_APP_SECRET`, `CADDY_MERCURE_JWT_SECRET`, `POSTGRES_PASSWORD`, `JWT_SECRET_KEY`/`JWT_PUBLIC_KEY`/`JWT_PASSPHRASE` (key contents), `ADMIN_PASSWORD` (#203), `MAILER_DSN`. The public dev defaults in `compose.yaml` stay on purpose; they only apply on localhost. `.gitguardian.yaml` marks the required-secret placeholders as not secrets.
- **`api/.dockerignore`** keeps local JWT/database keys, Symfony decrypt keys, `public/uploads/` and local PHPUnit files out of the image. A `frankenphp_prod` build should have an empty `config/jwt` and no `public/uploads`.
- **Caddy admin is loopback-only** (see *Caddy and Souin*). A prod override can't drop a merged port without `ports: !reset`, so port 2019 has to stay out of the base `compose.yaml`.

## Load testing (k6, #93)

`bin/load-test/launch.js` (+ `README.md`) is a manual tool, deliberately not in CI.
- `BASE_URL` required; pages from the sitemap (`PAGES` overrides, `MAX_PAGES` caps). Modes: `smoke`, `capacity`, `surge` (`PEOPLE`, default 100), `soak`.
- **The guard:** any non-local host needs `CONFIRM=yes`, checked before any request.
- `CACHE=warm|cold|mixed`; cold adds `k6cb=`. **Never make that a stripped tracking parameter**, or every cold request becomes a hit. `COLD_API=true` also bypasses the cache for API calls.
  - **Since #106, `k6cb` on pages is dropped by the query allowlist**, so a cold run's page requests are hits: that's the protection working (it simulates a cache-busting flood). To measure real render cost, add `k6cb` to `CACHE_QUERY_ALLOWLIST` on a test stack only. A single-machine cold `capacity`/`surge` run also trips the rate limit on its misses: set `RATE_LIMIT_ENABLED=false` (`CWA_API_` on a deploy) for it.
- `Accept-Encoding: gzip` is pinned (k6 can't decode brotli). Run from a VM (laptops time out ~300 users). After a cold run against a real site, flush Souin in the API pod.
- Warm runs on the dev stack show misses because dev pages expire after 60s.

## Git: splitting one file's changes across commits

`git add -p` is unavailable. With `git diff -U0` + `git apply --cached --unidiff-zero`, **`git apply` places each hunk by its header line numbers**, so skipping a hunk shifts every later one. `helm lint` won't catch misplaced YAML comments.
- Recompute each chosen hunk's new-side start from only the chosen hunks before it: `c = a + offset` (`+1` for a pure insertion, `-1` for a pure deletion), where `offset` sums `(new_count - old_count)` of the chosen hunks.
- After staging, check the remaining unstaged `-U0` diff is **exactly** the hunks you left out.

## `create-cwa` CLI

`packages/create-cwa/` (`npx create-cwa my-project`, GitHub #56). Prompts for name, CI/CD (GitHub Actions / GitLab CI / none), features and fixtures; downloads the template tag matching its own version (`--ref` overrides) via `giget`, removes unselected feature files (and `AppScaffold.php` plus `Parts/` when fixtures are declined; `UsersFixture.php` stays, so the admin is still created from `ADMIN_*` (#142), and nothing outside those may name a scaffold class), strips `@cwa-if:feature` blocks from `nuxt.config.ts`, writes a README, and offers to start the stack, which runs `sh bin/up` (#206; on Windows without `sh` it runs `docker compose up -d --wait` and prints the fixture step). `cwa-manifest.json` is the contract, read from the same tag; the CLI shows its questions' and choices' `hint`s.
- **The name** must be lower-case letters, digits and dashes (it's the directory and the compose project name), and the directory must be missing or empty, checked at the prompt, before downloading (#204).
- **Docker is decided before the download** (#204): on yes, `src/preflight.ts` checks `docker info`, ports 80, 443, 3001, 5432 and 8025 (naming the container and compose project, or the process, that holds one; 3001, 5432 and 8025 are hard-coded in `compose.override.yaml`, so the message names those lines) and warns under ~3.5 GiB of Docker memory. A failed check creates the project without starting the stack.
- **The host `pnpm install` is offered only when the stack isn't started now** (default **No**, editor types only), and runs before any `compose up` or `bin/up`: `app/node_modules` is bind-mounted, so a host install under the running dev server crashes it, and the container's own install already gives editors the types. `alwaysExclude` covers `packages/`, `CHANGELOG.md`, `publish-create-cwa.yml`, `publish-php-base.yml` (#208), `create-cwa-smoke.yml` (#215), `.gitlab/ci/template-only.yml` (#181) and the files that describe the template itself (#202): `LICENSE` (a client site isn't Silverback's MIT code), `SECURITY.md`, `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, `.github/ISSUE_TEMPLATE/` and `.github/pull_request_template.md`. Entries are exact paths (a trailing `/` for a directory), not globs. `engines.node` is `>=22.13.0`.
- **Flags (#215):** each choice has one (`--pipeline`, `--features a,b|all|none`, `--[no-]fixtures`, `--[no-]start`, `--[no-]install-deps`); a flag answers its question, so it isn't asked. `--yes` takes what Enter would (GitHub Actions, no features, fixtures, start the stack, no host install) and still asks for a missing name; `--ci` never prompts (a missing or invalid name is an error) and exits 1 when `bin/up` fails. Explicit `--start` fails before creating anything if Docker or a port check fails; without it a failed check only skips the start. **`--template-dir <path>`** copies a local checkout instead of downloading: `git ls-files --cached --others --exclude-standard` minus `export-ignore` paths, i.e. what GitHub's tarball holds, then the same excludes and stripping. Interactive runs with no flags are unchanged.
  - **Downloads leave out `export-ignore` paths** (`.gitattributes`; GitHub's tarball honours it), and `--template-dir` mirrors that. Only `README.md` is left there now: `.github/` was too until alpha.47, so a "GitHub Actions" project from create-cwa alpha.46 or older has no workflows.
- **Smoke job (#215):** `packages/create-cwa/smoke.sh <work dir>` builds the CLI if needed, runs `create-cwa cwa-smoke --ci --template-dir <repo> --pipeline none --features $SMOKE_FEATURES --[no-]fixtures --start` (so the CLI's own `bin/up` runs), then checks `bin/up` printed the login URL and `admin / admin`, `/login` has a password field and `POST /_api/login` as admin answers 204 (from inside php, which works under dind). Two variants: all features with fixtures, none without. GitHub: `create-cwa-smoke.yml` (paths filter + `workflow_dispatch`, guarded by `github.repository`, in `alwaysExclude`; not gated on `CWA_CI_DISABLED`). GitLab: `create-cwa smoke` in `.gitlab/ci/template-only.yml` (dind; on any branch when the CLI, manifest, `bin/up`, compose files, Dockerfiles, `api/frankenphp/`, lockfiles or fixtures change, else manual; never in schedules or with `CWA_CI_TEST_DISABLED`). Its project lives under `$CI_PROJECT_DIR` because dind shares only the builds directory, which the dev compose bind-mounts. It uses the Dockerfile's `cwa-php-base` (the last release's), as a `--ref main` install does. It needs ports 80/443/3001/5432/8025, so don't run it on a machine with a dev stack up; inside a privileged `docker:27-dind` container it's isolated.

## Decided against

- **`LOAD_DEMO_SCAFFOLD`** env flag to skip the scaffold but seed the admin. Loading fixtures *is* loading the scaffold; a site wanting an empty DB doesn't run them. Admin-only seeding belongs downstream. Don't port or re-propose it.
- **A build-time fixtures hook in `nuxt.config.ts`** (the old `LOAD_FIXTURES` `listen()` hook). It never ran and would have purged every table. Don't reintroduce one.
- **Probing a path Souin doesn't cache** for php readiness. Uncached `/_api` paths are excluded because they're auth-varying, so they either expose something or don't answer 200 anonymously. (`/_api/_/health` is excluded since #205 and the Docker healthchecks use it; moving the Kubernetes probes to it is a separate decision.)
- **A redirect ingress for retired hostnames** (#86). Take the old hostname offline via `KUBE_INGRESS_ALIAS_DOMAINS`; the TLS rotation makes that safe. A site that needs one can take the snippet from #86.
- **A PDB on the single API pod, or `minAvailable: 1` on SSR** (#78). Both block node drains.
- **Warming page HTML in the php pod's `postStart`** (#170). `purge_rendered_html` drops every page straight after the rollout anyway; during a rollout old PWA pods may render it with the old `/_nuxt` hashes (#71); on a first deploy there's no ready API endpoint for SSR; and once `/_api` is warm a page renders in ~150ms. The cold `/_api` was the cost, and #85's shared cache is the real fix. Revisit only with measurements.
- **A PWA `postStart` hook or helm `post-upgrade` Job for the deploy purge** (#71). The hook fires on every HPA scale-up; the Job is Kubernetes-only.
- **An update notice for the service worker.** Replaced by the silent update on navigation.
- **`experimental.asyncContext`** for the old `[nuxt] instance unavailable` SSR error. It was resolved by dependency updates; nothing to apply.
- **Dropping `Accept` from the Souin key in favour of `Vary`.** See *Caddy and Souin*.
